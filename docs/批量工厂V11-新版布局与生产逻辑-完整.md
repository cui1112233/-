## 2. 产品定位：批量工厂是“水货生产”的小说前贴版本（已确认）

- **水货生产**：主要做漫剧解说。
- **批量工厂**：主要做小说前贴。

两者在产品壳层、个人作品、工作台、预设 / Prompt / 图片 / 视频生产习惯上尽量对标和复用；小说获取、小说前贴、121 发布、多书批量等由批量工厂自己的业务逻辑负责。

核心映射：

`水货生产：一行一个分镜 → 批量工厂：一行一本小说`

不是复制水货的数据结构，而是复用成熟的作品生命周期和交互，再换成小说前贴业务。

顶部主入口：

`小说列表 / 引擎配置 / AI推理 / 批量操作 / 取消操作 / 任务/日志 / 上传121`

- 小说列表：对应水货生产“分镜调整”。
- 引擎配置：保持原名。
- AI推理：保持原名，不改成 AI导演。
- 批量操作：只负责实际媒体生成、重试、合并。
- 上传121：替换水货生产“导出剪映”的位置。
- 人物场景预设：不是全局顶部入口，是单书工作区。
- 原“资产/导演”主列：新版直接叫“预设”。

## 3. 小说获取 → 批量工厂 → 个人作品（已确认）

### 3.1 进入即创建作品并打开小说列表

废弃旧流程：

`Intake → 待建立批次 → 点击创建 V11 批次 → 工作台`

新版：

```text
小说获取
↓
进入批量工厂
↓
系统自动创建作品 / 文档
↓
直接进入小说列表
```

自动创建作品不等于自动执行 AI、生成图片、生成视频或上传121。

### 3.2 个人作品卡片

左上角显示生产模式标签：

- `批量工厂`
- `水货生产`

主标题才是文档名，例如：

```text
[批量工厂]
2026-09-11-001
```

文档名允许重命名。重命名只改显示名称，不改 projectId、bookId、任务关系、来源关系、121 发布绑定。

### 3.3 30 本小说 = 1 个批量工厂作品文档

默认按 30 本一档自动拆分：

- 1～30 本 → 1 个文档
- 31～60 本 → 2 个文档
- 61～90 本 → 3 个文档
- 91～120 本 → 4 个文档

100 本示例：

```text
100 本
↓
├─ 2026-09-11-001 → 30 本
├─ 2026-09-11-002 → 30 本
├─ 2026-09-11-003 → 30 本
└─ 2026-09-11-004 → 10 本
```

### 3.4 同一次拆分出来的多个文档

创建时复制同一套初始配置：

- 引擎配置
- AI推理配置
- 其他作品级统一设置

创建完成后各文档独立保存、独立修改，不再联动。

`001 修改 ≠ 自动修改 002 / 003 / 004`

实现层可保留隐藏 source/import group id 追踪同一次导入，但不作为用户可见交互。

## 4. 小说获取内容版本、内容范围、二次编辑、爆款、121发布（本轮已确认业务意图）

这一层必须把“来源内容”和“视频生产内容”拆开，禁止为了制作前贴而破坏小说获取保存的完整内容。

### 4.1 小说获取传入的是“已经选定的完整内容版本”

小说获取本身可能存在不同内容结果，例如：

- 原文
- 去敏感化后的原文
- 不去敏感化的原文
- AI1 文
- AI2 文
- 以后小说获取继续增加的其它版本

批量工厂不重新决定使用哪个版本，而是接收小说获取本次实际送入的那个版本，并保留其完整内容。

建议概念：

- `sourceVariant`：本次来自小说获取的内容版本类型。
- `sourceContentFull`：该版本的完整内容，是不可被批量工厂二次编辑直接覆盖的来源真值。

### 4.2 内容范围 = 前 N 条有效正文，只决定前贴生产区

`内容范围：5`：忽略空白行，取前 5 条有效正文。

`内容范围：10`：忽略空白行，取前 10 条有效正文。

空行不计数。

```text
sourceContentFull
↓
按原始位置识别有效正文
↓
内容范围 N
↓
sourceFrontContent = 前 N 条有效正文
sourceRemainder = 第 N 条有效正文之后的剩余完整内容
```

小说列表里“原文/内容”的当前生产展示区，可以展示这个范围内的内容，而不是把完整来源正文真的裁掉。

### 4.3 支持二次编辑

用户可以直接编辑内容范围内展示的前贴文本。

建议保存为独立工作文本：

`workingFrontContent`

它用于当前小说的视频生产，不覆盖 `sourceContentFull`。

### 4.4 “爆款”是前贴文本的 AI 改写动作，不再作为另一个大生产模式

小说内容旁边提供“爆款”动作：

```text
当前前贴文本
↓ 点击【爆款】
AI 生成爆款开头 / 爆款版本
↓
直接展示改写结果
↓
用户点击【替换】
↓
workingFrontContent = 爆款结果
```

如果用户不点击替换，原当前工作文本保持不变。

因此此前把“原文直转 / 爆款开头”理解成两个互斥的大生产模式不够准确。新版更接近：**小说获取传入一个来源版本，内容范围形成前贴工作区；用户可以手动二次编辑，也可以用“爆款”生成候选并替换。**

### 4.5 “改文 / 不改文”开关控制的是 121 发布正文，而不是视频是否使用改写文本

无论开关是什么，只要用户已经二次编辑或接受了爆款替换，当前 `workingFrontContent` 都可以作为视频生产文本，去做资产、分镜、视频 Prompt、画面 Prompt（如启用）、图片和 VIDEO。

#### 不改文

```text
视频生产：使用 workingFrontContent
121正文：继续使用小说获取传入的完整 sourceContentFull
```

也就是说，改写只服务于前贴视频，121 上传正文仍保持小说获取那一版（原文 / 去敏感化 / AI1 / AI2 等）。

#### 改文

```text
视频生产：使用 workingFrontContent
121正文：workingFrontContent + sourceRemainder
```

含义是：把原来内容范围覆盖的前 N 条有效正文替换成用户最终二次编辑 / 爆款后的内容，再拼接第 N 条有效正文之后的完整剩余正文。

例如：

```text
小说获取完整内容 = 4000字
内容范围 = 5
前5条被二次编辑/爆款替换
改文 = 开
↓
121正文 = 改后的前贴内容 + 原第5条有效正文之后的剩余内容
```

### 4.6 爆款内容是否上传，不需要再单独增加一个“爆款上传”开关

推荐规则：

- 爆款生成后未替换 → 不影响任何内容。
- 爆款生成并点击替换 → 成为 workingFrontContent。
- `不改文` → 爆款 workingFrontContent 只做视频，121仍传 sourceContentFull。
- `改文` → 爆款 workingFrontContent 替换前贴段后，与 sourceRemainder 拼接上传121。

这样“爆款要不要上传”由现有 `改文 / 不改文` 一个开关统一决定，避免再增加重复开关。

### 4.7 数据必须可逆，禁止破坏性覆盖来源正文

推荐至少保留这些概念：

```text
sourceVariant
sourceContentFull
contentRangeN
sourceFrontContent
sourceRemainder
workingFrontContent
publishRewriteEnabled   // 改文/不改文
publishContent          // 上传时计算出的正文
```

`publishContent` 应在上传前根据开关计算，不要把 `sourceContentFull` 改写掉。这样用户在“改文/不改文”之间切换时无需恢复数据，也不会因为做一次爆款就丢失小说获取原始版本。

### 4.8 与旧 maxTxt 区分

小说获取旧 `maxTxt / 截取字数` 是按字数。批量工厂 `内容范围：5 / 10 / ...` 是按有效正文行数，两者不是同一语义。

## 8. 固定开头（本轮补充，单个视频语义基本确认）

固定开头与“爆款”完全不是一回事：

- **爆款**：改当前前贴文字内容。
- **固定开头**：控制最终哪些分镜被真正转成视频，以及首个视频的目标格式 / 时长。

用户当前明确的“单个视频”思路：

无论内容范围是 10 行还是 50 行，如果：

```text
固定开头 = 单个视频
VIDEO 格式/时长 = 10s
```

则最终只把第一个分镜作为 10s VIDEO 生产；其它分镜提示词不继续转成 VIDEO。

如果选择 15s，则第一个分镜按 15s VIDEO 目标生产，其它分镜提示词不转成视频。

这里不能把“内容范围”误解成“一行=一个视频”。内容范围仍然可以供 AI 理解上下文；固定开头的单个视频模式决定最终媒体只生产首个分镜 / VIDEO01。

**仍待确认一个细节：单个视频模式下，其它分镜 Prompt 是仍然生成并保留、只是不给视频模型执行；还是 AI 阶段就只产出一个分镜 Prompt。**

“多个视频”模式的精确停止规则也待下一步确认，不自行猜测。

## 9. 分镜与 VIDEO：1:1（硬规则）

```text
一本小说
├─ 分镜01 → VIDEO01
├─ 分镜02 → VIDEO02
├─ 分镜03 → VIDEO03
└─ ...
```

不存在 VIDEO 下再嵌套 Shot。

左右箭头切换当前分镜，并同步切换：预设、人物/场景/道具引用、视频提示词、画面提示词（若有）、画面图片、VIDEO结果、任务状态。

如果某分镜从未生成画面提示词，则不显示“画面提示词”Tab。

## 10. VIDEO 目标时长 / 请求时长 / 实际时长（硬规则）

`≤10s / ≤15s` 是单个 VIDEO 的能力上限，不是必须生成满。

建议区分：

- `targetDurationSec`：AI / 业务目标
- `requestedDurationSec`：真正发给 provider
- `actualDurationSec`：provider 成品真实时长

目标6s、模型输出10s → 接受10s，不裁剪当前单段。模型仅支持固定档位时，由 adapter 选择可用档位；实际时长仍按真实结果记录。

## 11. 人物 / 场景 / 道具：有图不用词（硬规则）

| 当前分镜引用对象 | 对象图存在 | 基础设置开启 | 最终输入 |
|---|---|---|---|
| 是 | 是 | 是 | 只传图片，不传该对象文字 Prompt |
| 是 | 是 | 否 | 只传图片，不传该对象文字 Prompt |
| 是 | 否 | 是 | 传该对象文字 Prompt |
| 是 | 否 | 否 | 什么都不传 |
| 否 | 任意 | 任意 | 什么都不传 |

基础设置只控制无图时的文字回退，不控制已有图片上传。

---

## 12. 画面提示词永远不直接进入视频生成（硬规则）

`画面提示词` 只用于生成 `画面图片`。

视频生成：

- 有画面图片 → 上传画面图片
- 只有画面提示词、没有画面图片 → 忽略画面提示词
- 绝不把画面提示词编译进视频 Prompt

旧 `visualPrompt → compiledPrompt → 视频模型` 语义必须废弃 / 重构。

---

## 13. 系统自动判断文生 / 图生

不增加用户选择“文生视频 / 图生视频”。系统按当前分镜已有资产自动决定：

- 有画面图片 → 使用
- 当前分镜引用的人物 / 场景 / 道具有图 → 使用相关图
- 某对象无图 → 仅基础设置允许时使用该对象文字 Prompt
- 无视觉图 → 实际走纯文本视频

同一分镜允许多张相关参考图，例如：

`画面图片 + 女主图 + 男主图 + 客厅图 + 手机图`

超过模型上限时由 capability / adapter 显式处理，业务层不能擅自静默丢图。


## 15. 跟随音频：两个独立能力（已确认）

两个都关、单独开任意一个、两个同时开都允许。

### 15.1 生成阶段按音频时长约束

AI按真实音频总长规划分镜目标时长；provider 实际输出可以不同，不按单段强裁。

### 15.2 合成阶段按音频时长匹配

`自动倍率 = 视频实际总时长 ÷ 音频实际时长`

- >1.0x：加速
- =1.0x：原速
- <1.0x：允许慢放拉长

用户手动修改倍率时，直接覆盖自动推荐值，不叠乘。

TTS / 音频主要用于时长和节奏，不默认混入最终视频音轨。

## 16. 画面图片生成

当前分镜：

- 对象有图 → 用图，不重复同对象 Prompt
- 对象无图 → 可用对应资产文字预设
- + 当前分镜画面提示词
- → 画面图片

批量“画面图”只处理实际有画面提示词的分镜。

待确认：画面图链路中“对象无图 → 文字 Prompt 回退”是否也受基础设置开关控制。

## 18. 合并

- 按分镜 / VIDEO 顺序合并

- 某 VIDEO 重生成后旧合并结果失效，可重新合并
- 原始 VIDEO 不因重新合并删除

待确认：失败片段是否可跳过、all-or-nothing、输出命名、重复合并历史版本。

- 水货已有 project / 个人作品 / studio 生命周期，批量工厂优先对标复用。

## 22. 已废弃 / 被新规则覆盖的旧思维

- 大一统“生产统一设置” → 拆成引擎配置 + AI推理。
- “画面提示词直接进视频 Prompt” → 废弃。
- “有对象图仍重复注入对象 Prompt” → 废弃。
- “音频比视频长不允许慢放” → 废弃。
- “状态中心 + 自由布局是主页面核心” → 改为水货式一行一本小说。
- “只支持失败 VIDEO 重试” → 改为支持选书并按失败阶段重试。
- “Intake 后必须手动创建批次” → 废弃。
- “原文直转 / 爆款开头是两个互斥大生产模式” → 被本轮内容工作区设计取代：来源版本 + 内容范围 + 二次编辑/爆款候选 + 改文/不改文发布决策。
