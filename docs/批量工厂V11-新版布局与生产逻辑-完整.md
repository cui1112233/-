## 2. 产品定位：批量工厂是“水货生产”的小说前贴版本（已确认）

- **水货生产**：主要做漫剧解说。
- **批量工厂**：主要做小说前贴。

两者在产品壳层、个人作品、工作台、预设 / Prompt / 图片 / 视频生产习惯上尽量对标和复用；小说获取、小说前贴、121 发布、多书批量等由批量工厂自己的业务逻辑负责。

核心映射：

`水货生产：一行一个分镜 → 批量工厂：一行一本小说`

顶部主入口：

`小说列表 / 引擎配置 / AI推理 / 批量操作 / 取消操作 / 任务/日志 / 上传网络`

其中：

- 小说列表：点击后展开当前作品的上传书籍信息（书名、bookId、书城、男女频、类型、来源）；关闭后回到水货式制作区。制作区外层仍遵守“一行一本小说”。
- 引擎配置：保持原名。
- AI推理：保持原名，不改成 AI导演。
- 批量操作：只负责实际媒体生成、重试、合并。
- 上传网络：替换水货生产“导出剪映”的位置，点击后下拉 `提交选中 / 提交全部`，实际目标为121发布链路。
- 人物场景预设：不是全局顶部入口，是单书工作区。
- 原“资产/导演”主列：新版直接叫“预设”。

## 3. 小说获取 → 批量工厂 → 个人作品（已确认）

### 3.1 两个入口进入同一批量工厂作品并打开小说列表

批量工厂有两个入口，最终进入同一套作品、小说、分镜、VIDEO、合并和上传网络生产逻辑：

- **手动新建批量**：水货生产个人作品页中的 `批量工厂` 按钮直接弹出 `新建批量`，不跳转独立页面。弹窗复用最新小说获取的书单输入协议：`书城/平台 + 输入格式 + 列顺序预设 + 自定义列顺序 + 多行书籍清单`。清单解析并保留 `bookId`、书名、男女频、标签、评级、推荐理由等元数据和原始输入行；手动入口只取每本小说的原始正文，不接受用户粘贴或上传正文。
- **小说获取导入**：小说获取把用户已经选择或改写后的完整正文、`bookId`、书名、书城及来源信息直接传入批量工厂。

两条入口的区别只在正文来源，不能分叉为两套生产逻辑：

```text
手动新建批量 ─┐
              ├─→ 创建一个批量工厂作品 → 直接打开小说列表
小说获取导入 ──┘
↓
同一套单书生产、批量操作、合并和上传网络
```

自动创建作品不等于自动执行 AI、生成图片、生成视频或上传121；只有用户在 `新建批量` 中明确开启 `自动` 并设定执行时间，才创建定时自动生产任务。

### 3.1.1 新建批量的“自动”与“内容范围”（已确认）

`新建批量` 除了书籍行，还提供两个作品创建参数：

- **自动**：默认关闭。关闭时，只创建批量工厂作品和小说列表；用户之后从小说列表或批量操作手动发起生产。
- **定时执行时间**：只有打开 `自动` 后显示且必填。保存时，作品与全部小说立即入库，但小说状态为 `定时待执行`。到时间后，系统将本次作品的定时小说释放到自动生产队列。
- **内容范围**：每本小说按有效正文行数取前 N 条，**只控制工作台“小说正文”列的展示**。例如内容范围 `5` 时，外层小说行只展示前 5 条有效正文；它不裁剪保存正文，也不限制后续121上传正文。
- **内容截取**：与内容范围并列的小控件，默认 `4000 字`。手动入口点击“获取内容”时按此长度抓取；保存、后续生产和121上传都使用本次实际截取到的正文。例如选择 `4000`，后续上传的就是这 4000 字内容。
- **确认创建**：自动关闭时，主操作只创建一个批量工厂作品及其中全部小说，不启动 AI、图片、VIDEO、合并或121上传。

定时自动生产针对每本小说走完整既有生产链，而不是只做抓取或只生成任务：

```text
定时到点
↓
手动入口：按 bookId / 书城获取原始正文
小说获取入口：使用已传入的已选内容版本
↓
按内容截取长度取得并保存正文；内容范围只决定工作台展示条数
↓
按作品或单书 override 生成提示词、画面图片和 VIDEO
↓
按既定规则合并最终视频
↓
上传网络 → 提交 121 → 真实回读确认
```

自动链路中的 `121 已完成` 必须仍以真实回读为准；请求已发出、排队或上传中均不能写成完成。

取消定时只取消本次尚未到点 / 尚未释放的小说任务，不删除作品、小说记录和已经生成的内容；已释放到生产队列或已经提交 121 的任务按各阶段既有取消与回读规则处理。

### 3.1.2 手动新建批量的书单控件必须对应小说获取（已确认）

`新建批量` 的书单区域不是一组模拟字段，必须复用小说获取工作台当前的输入协议和平台数据：

- **书城**：读取小说获取工作台的当前平台表，仅显示 `visible !== false` 的项；下拉项的值必须是平台表原始 `platformId`，不能把“番茄”等显示名称当作 ID 写入批量记录。
- **书城展示名**：每本小说同时保存小说获取返回的 `platformName` 作为展示元数据；界面只显示书城名称，不显示内部数字 `platformId`。历史书单若尚未保存名称，则按当前小说获取平台表回填展示名。
- **输入格式 / 列顺序预设 / 自定义列顺序 / 多行书单**：沿用小说获取处理页的同名枚举和值。每行仍是一部小说，解析规则和书单元数据与小说获取一致。
- **完整元数据预设**：默认列顺序为 `书籍ID / 书名 / 男女频 / 风格 / 标签 / 推荐理由 / 评级`；这七项随每本小说保存，并在小说列表、详情和后续发布配置中可读。其他小说获取兼容预设继续保留。
- **确认创建**：相当于小说获取“开始处理”前的书单校验与解析，但其结果是创建一个批量工厂作品及全部小说记录；不会调用小说获取改文、抓取、AI 或网站提交流程。
- **校验失败**：平台表没有加载成功、未选择有效书城、书单为空或解析失败时，禁止创建；不能用硬编码默认书城或伪造 ID 继续写入。
- **后续生产**：手动批量在真正开始制作或定时释放时，使用保存的 `platformId + bookId` 获取原始正文；小说获取导入则继续使用其已选择的完整内容版本。

因此，批量工厂和小说获取共用“书城与书单协议”，但不共用一次点击后的处理动作：前者创建小说前贴作品，后者执行小说获取处理任务。

### 3.2 个人作品卡片

左上角显示生产模式标签：

- `批量工厂`
- `水货生产`

主标题才是文档名，例如：

```text
[批量工厂]
2026-09-11-001
```

文档名允许重命名。重命名只改显示名称，不改 projectId、bookId、任务关系、来源关系、121 发布绑定。

### 3.3 本次选择的全部小说 = 1 个批量工厂作品文档

手动新建批量或小说获取一次传入多少本小说，点击顶部“小说列表”后就必须在**同一个批量工厂作品文档**中显示多少条上传书籍信息；不再按 30 本自动拆分作品。关闭小说列表回到制作区时，外层序号 1、2、3…分别对应这 N 本小说；每行承载该书的内容和制作，书内生成的分镜 / VIDEO 不得成为外层小说序号。

例如一次选择 100 本：

```text
2026-09-11-001（批量工厂作品）
└─ 小说列表：100 本
```

### 3.4 作品级配置与小说级配置

创建时在作品级保存引擎配置、AI推理配置和其他统一设置；单本小说及其分镜 / VIDEO 仍可按既定 override 规则覆盖。

实现层可保留 sourceTaskId 或 import group id 追踪来源，但不作为用户可见交互。

## 4. 小说获取内容版本、内容范围、二次编辑、爆款、121发布（已确认）

### 4.1 小说获取传入的是“已经选定的完整内容版本”

小说获取可能传入：原文、去敏感化原文、不去敏感化原文、AI1、AI2、以后新增版本等。批量工厂接收本次实际送入的那个版本，并保留完整内容。

建议概念：

- `sourceVariant`：本次来自小说获取的内容版本类型。
- `sourceContentCaptured`：本次实际保存的正文。手动入口由“内容截取”决定（例如 4000 字）；121上传使用该正文，禁止被工作台预览设置覆盖。

### 4.2 内容范围 = 工作台展示前 N 条有效正文

`内容范围：5` = 忽略空白行，在外层小说行展示前 5 条有效正文。

`内容范围：10` = 忽略空白行，在外层小说行展示前 10 条有效正文。
空行不计数；该值只影响展示，不能裁掉保存内容或121上传内容。

```text
内容截取 M（默认 4000 字）
↓
sourceContentCaptured = 本次实际获取并保存的正文，后续上传使用它
↓
内容范围 N
↓
workbenchPreview = 前 N 条有效正文（仅展示）
```

内容范围只决定工作台展示，不裁掉实际保存正文。内容截取才决定本次获取和后续上传的正文长度。

### 4.3 支持二次编辑

用户可直接编辑内容范围内的前贴文本，保存为独立工作文本：

`workingFrontContent`

它用于视频生产，不覆盖 `sourceContentCaptured`。

### 4.4 “爆款”是前贴文本的 AI 改写动作

```text
当前前贴文本
↓ 点击【爆款】
AI生成爆款候选
↓
展示改写结果
↓
用户点击【替换】
↓
workingFrontContent = 爆款结果
```

若不点击替换，则当前工作文本保持不变。

“原文直转 / 爆款开头”不再是两个互斥的大生产模式；新版是：来源版本 + 内容范围 + 手动二次编辑 / 爆款候选替换。

### 4.5 “改文 / 不改文”控制121正文，不控制视频是否使用改写文本

无论开关是什么，只要用户已经二次编辑或接受爆款替换，`workingFrontContent` 都可以用于视频生产。

#### 不改文

```text
视频生产：workingFrontContent
121正文：sourceContentCaptured
```

#### 改文

```text
视频生产：workingFrontContent
121正文：workingFrontContent（仅当用户明确采用改文版本）
```

即只替换内容范围覆盖的前 N 条正文，后面继续拼接小说获取保存的剩余正文。

### 4.6 爆款是否上传不再增加独立开关

- 爆款未替换 → 不影响当前工作文本。
- 爆款替换成功 → 成为 `workingFrontContent`。
- 不改文 → 爆款只做视频，121 仍传 `sourceContentCaptured`。
- 改文 → 121 传用户明确确认后的改文版本；不能因为“内容范围”预览条数而拼接或裁掉正文。

### 4.7 数据必须可逆

至少保留：

```text
sourceVariant
sourceContentCaptured
contentRangeLines
contentCaptureCharacters
workbenchPreview
workingFrontContent
publishRewriteEnabled
publishContent
```

`publishContent` 在上传前根据开关计算，不覆盖 `sourceContentCaptured`。

### 4.8 与旧 maxTxt 区分

小说获取旧 `maxTxt / 截取字数` 是按字数；批量工厂 `内容范围：5 / 10 / ...` 是按有效正文行数，两者不是同一语义。

## 5. 单书配置（已确认）

每本小说有自己的：人物场景预设、引擎配置、AI推理。默认跟随作品统一配置；只有用户真正改动的字段形成单书 override。

### 5.1 单书 → 人物场景预设

对标水货生产：左侧 Prompt，右侧图片。负责当前书实际的人物 / 场景 / 道具 Prompt 和图片，包括查看、编辑、保存、重新生成、生成图片、替换图片。

`AI推理 → 资产设置` = 批量/全局资产 Prompt 生成规则。  
`单书 → 人物场景预设` = 当前书实际资产 Prompt + 图片。

### 5.2 单书配置五分区（已确认并落地）

工作台每一行在“小说正文”和“预设”之间放置单书配置区；它不是单一总按钮，而是固定五个分区按钮：`引擎配置 / 资产设置 / 约束设置 / 视频设置 / 画面设置`。点击任一分区只弹出该书、该分区的居中卡片弹窗。

- **引擎配置**：选择当前书的文本模型、图片模型、视频模型、视频引擎、画幅及生产模式。
- **资产设置**：选择已发布且槽位匹配的人物场景提取、人物、场景、道具预设；“维护当前书人物场景预设”必须直达本书真实的人物 / 场景 / 道具 Prompt 和图片编辑器，不能用展示用假资产代替。
- **约束设置**：复用剧本生成的五层约束：基础设定、画面前缀词、画质约束、画面限制、负面提示词。
- **视频设置**：选择视频提示词预设，并设置该书的 VIDEO 时长上限、单个/多个 VIDEO 与固定时长。
- **画面设置**：单独选择画面提示词预设；默认可不启用，绝不与视频提示词混写。

所有分区默认继承当前批量作品配置。保存时只写当前分区真实改变的字段或 AI 模块；已有的其它单书模块必须保留。恢复作品配置只移除当前分区的单书 override，立即重新继承作品配置。有效优先级始终是 `作品 → 单书 → 单分镜 / VIDEO`。单书 `aiPromptConfig` 按资产、约束、视频、画面四个模块深度合并，不能因保存其中一个模块覆盖其它模块。行内状态必须如实显示“继承作品配置 / 已单书覆盖 / 本书未启用”；资产区附带当前书真实人物、场景、道具数量。

## 6. 引擎配置（模型配置 + 发布统一）

顶部 Tab：`[模型配置] [发布统一]`

### 6.1 模型配置

- 视频：视频模型 / VIDEO 时长 / 画幅 / 匹配音频
- 图片：图片模型
- 文本：文本模型

批量工厂不填写 API Key / personal_api 凭据；凭据由个人中心 / 管理端负责，批量工厂只选择账号已授权模型。

业务层只决定“应该传什么”；供应商语法、参考图上限、时长档位、画幅等由 provider adapter / capability 层转换。禁止业务数据写死 `@图片1`；不兼容必须显式提示，不能静默丢数据。

### 6.2 配置继承与单分镜 / 单 VIDEO Override（已确认）

保留单分镜 / 单 VIDEO 独立覆盖设置。当前已确认允许单分镜覆盖：视频模型、VIDEO 时长 / 时长上限、画幅。

生效优先级：

```text
作品统一配置
↓
单书 override（若有）
↓
单分镜 / 单VIDEO override（若有）
↓
effectiveEngineConfig
```

未覆盖字段继续向上继承。单分镜修改不能反向覆盖整本小说或作品统一设置。是否允许单分镜覆盖“匹配音频”等其它字段，后续再确认。

### 6.3 发布统一必须保留“版本对应配置档”及网站同步能力（已确认）

`发布统一` 不是只放“改文 / 不改文”和121通道状态；它还必须保留原先的 **版本对应配置档** 这一组网站发布能力。

建议界面结构：

```text
引擎配置
└─ 发布统一
   ├─ 版本对应配置档
   ├─ 改文 / 不改文
   ├─ 保存网站提交配置
   ├─ 环境自检
   ├─ 同步网站配置档
   └─ 同步网站风格类型
```

硬规则：

- **版本对应配置档**：必须作为发布统一里的明确可见配置区 / 入口保留，不能再被“解析输入”或单纯的通道状态替代。
- **保存网站提交配置**：保存当前用于网站/121提交的配置映射；保存后重新进入仍应回读到同一配置，不能出现“保存了再进去又没了”。
- **环境自检**：检查当前发布环境是否具备真实提交条件，例如121登录 / 授权会话、Browser Worker / 浏览器桥接或真实API通道、必要网站配置是否可用。环境自检只检查，不提交小说，也不能把 `healthy` 当作121业务提交成功。
- **同步网站配置档**：从121网站 / 当前真实来源同步网站提交所需的配置档，供“版本对应配置档”选择或更新；同步失败必须显示真实原因，不能用本地默认值伪装同步成功。
- **同步网站风格类型**：从121网站同步当前可用的风格类型列表，供发布配置选择；同样必须来自真实网站/来源回读，不能写死一份假数据冒充同步。
- 上述“保存 / 自检 / 同步”都是发布配置与环境动作，不等于真正上传。真正提交小说仍统一从顶部 `上传网络 → 提交选中 / 提交全部` 发起。
- `10秒轮询 / 10分钟超时` 属于后端运行参数，不要求普通用户在“发布统一”里手动填写。

因此“发布统一”的职责是：**维护网站发布配置 + 版本对应配置档 + 网站配置/风格同步 + 环境自检 + 改文策略；真正提交动作仍在顶部上传网络。**

## 8. 固定开头（单个视频 / 多个视频语义已确认）

固定开头与“爆款”完全不同：爆款改当前前贴文字内容；固定开头控制最终哪些分镜真正转成视频，以及首个视频目标格式 / 时长。

### 8.1 单个视频

AI 仍正常分析全部当前生产文本并生成全部分镜 Prompt，但媒体层只执行 `分镜01 / VIDEO01`。

```text
分镜01 Prompt → VIDEO01
分镜02 Prompt → 保留，不执行视频
分镜03 Prompt → 保留，不执行视频
...
```

10s 模式就把 VIDEO01 作为10s目标；15s同理。

### 8.2 多个视频

就是正常完整生产逻辑：AI 根据 `workingFrontContent + 视频提示词 + 约束设置` 正常得到多少有效分镜，就执行多少 VIDEO。不增加固定数量，不增加额外停止条件。

```text
单个视频 = AI照常得到全部分镜，媒体层只执行VIDEO01
多个视频 = AI照常得到全部分镜，媒体层执行全部分镜/VIDEO
```

## 9. 分镜与 VIDEO：1:1（硬规则）

```text
一本小说
├─ 分镜01 → VIDEO01
├─ 分镜02 → VIDEO02
├─ 分镜03 → VIDEO03
└─ ...
```

不存在 VIDEO 下再嵌套 Shot。左右箭头切换当前分镜，并同步切换预设、人物/场景/道具引用、视频提示词、画面提示词（若有）、画面图片、VIDEO结果、任务状态。如果某分镜从未生成画面提示词，则不显示“画面提示词”Tab。

### 9.1 每个分镜保留“1 个主框 + 4 个候选框”（已确认）

对标水货生产的片段库交互。这里的 4 个小框不是 4 个额外分镜，而是**同一个分镜 / VIDEO 的历史候选版本**。

```text
当前分镜 / VIDEO03

┌──────────────┐   ┌──────┐ ┌──────┐
│ 主框         │   │候选1 │ │候选2 │
│ 当前最终版本 │   ├──────┤ ├──────┤
│ merge使用它  │   │候选3 │ │候选4 │
└──────────────┘   └──────┘ └──────┘
```

规则：

- 左侧大框 = 当前分镜的 `主框 / 当前选中视频版本`。
- 右侧固定展示 4 个候选槽，用于保存该分镜重新生成前后的其它成功版本。
- 用户对单独分镜不满意、修改 Prompt / 配置后重新生成时，不应直接把旧成功视频彻底覆盖掉；新成功版本成为当前主框，上一主框进入候选槽。
- 用户点击任意候选视频，可将其切换为这个分镜当前的主框；原主框回到候选集合，而不是删除。
- “主框”是用户当前确认给后续合并使用的版本，不等于“时间上最新生成的版本”。用户可以主动切回旧候选作为主框。
- 重新生成只影响当前分镜的视频版本集合，不改变其它分镜。

### 9.2 合并永远读取每个分镜当前主框

例如：

```text
分镜01 → 主框版本 V1-2
分镜02 → 主框版本 V2-1
分镜03 → 主框版本 V3-4
↓
最终合并 = V1-2 + V2-1 + V3-4
```

候选框中的视频不会自动参加合并。只有先被用户切换为该分镜主框，才成为下一次合并输入。

### 9.3 候选槽占满后的淘汰规则（已确认）

每个分镜前台最多保留：`1 个主框 + 最近 4 个候选版本`。

当 4 个候选槽已经全部占满，又生成一个新的成功 VIDEO 版本时：

1. 新生成的成功版本成为当前主框。
2. 原主框进入候选集合。
3. 若候选数量因此超过 4 个，按生成时间淘汰最老的候选版本。
4. 主框永远不能因为候选槽满而被系统自动删除。
5. 用户主动点击候选切换主框只是在现有 5 个版本之间交换当前选中状态，不触发淘汰。

因此用户始终看到当前主框 + 最近 4 个可回退候选，既能反复修改单分镜，也不会无限堆积前台版本。

### 9.4 被淘汰候选 = 真删除旧候选视频文件（已确认）

当某个候选因为“只保留最近4个候选”规则被淘汰后，不只是从界面隐藏，而是执行真实存储清理：

- 从该分镜候选版本集合中移除。
- 删除对应 TOS / 对象存储中的旧候选视频文件，避免长期堆积无用媒体。
- 可保留轻量日志 / 元数据（例如版本ID、生成时间、provider、删除状态）用于排查，但不再保留可播放的视频实体。
- 只有已经确认不再属于“当前主框 / 4个候选槽”的版本才允许进入删除流程；系统不得误删当前主框。
- 用户在现有主框与候选之间手动切换，不属于淘汰，不触发物理删除。
- 若对象存储删除失败，应记录清理失败并进入可重试清理，不得把“删除失败”伪装成成功。

因此单分镜媒体存储上限与前台逻辑保持一致：正常情况下最多保留当前主框 + 4 个候选视频实体。

## 10. VIDEO 目标时长 / 请求时长 / 实际时长（硬规则）

`≤10s / ≤15s` 是单个 VIDEO 的能力上限，不是必须生成满。

区分：

- `targetDurationSec`：AI / 业务目标
- `requestedDurationSec`：真正发给 provider
- `actualDurationSec`：provider 成品真实时长

目标6s、模型输出10s → 接受10s，不裁剪当前单段。模型仅支持固定档位时，由 adapter 选择可用档位；实际时长按真实结果记录。

## 11. 人物 / 场景 / 道具：有图不用词（硬规则）

| 当前分镜引用对象 | 对象图存在 | 基础设置开启 | 最终视频输入 |
|---|---|---|---|
| 是 | 是 | 是 | 只传图片，不传该对象文字 Prompt |
| 是 | 是 | 否 | 只传图片，不传该对象文字 Prompt |
| 是 | 否 | 是 | 传该对象文字 Prompt |
| 是 | 否 | 否 | 什么都不传 |
| 否 | 任意 | 任意 | 什么都不传 |

基础设置只控制最终视频链路中“无图时的文字回退”；不控制已有图片上传，也不控制画面图链路的资产文字补齐。

**例外：若对象图虽然存在，但因为当前视频模型参考图上限而被能力层主动挤出，则按第13.1节执行“模型能力降级”，该对象允许改用文字 Prompt 补偿。这不是普通的有图场景，不视为违反“有图不用词”。**

## 12. 画面提示词永远不直接进入视频生成（硬规则）

`画面提示词` 只用于生成 `画面图片`。

视频生成：有画面图片就上传画面图片；只有画面提示词、没有画面图片则忽略画面提示词；绝不把画面提示词编译进视频 Prompt。旧 `visualPrompt → compiledPrompt → 视频模型` 语义必须废弃 / 重构。

## 13. 系统自动判断文生 / 图生

不增加用户选择“文生视频 / 图生视频”。系统按当前分镜已有资产自动决定：有画面图片就使用；当前分镜引用的人物 / 场景 / 道具有图就使用相关图；某对象无图时，仅基础设置允许时使用该对象文字 Prompt；无视觉图则实际走纯文本视频。

同一分镜允许多张相关参考图，例如：`画面图片 + 女主图 + 男主图 + 客厅图 + 手机图`。

### 13.1 参考图超过模型上限：自动降级 + 文字补偿（已确认）

批量工厂不因为参考图数量超过当前模型上限就默认阻止整批生产；由 capability / provider adapter 读取当前模型真实参考图上限，并按固定优先级选择实际上传的图片：

```text
1. 当前分镜画面图片
2. 当前分镜引用的人物图
3. 当前分镜引用的场景图
4. 当前分镜引用的道具图
```

同一优先级内存在多张图片时，按当前分镜 `presetRefs` / 明确引用顺序稳定排序，不能随机选择。

例如当前需要：

```text
画面图 + 女主图 + 男主图 + 客厅图 + 手机图 = 5张
模型最多支持3张
```

实际上传：

```text
画面图 + 女主图 + 男主图
```

客厅图、手机图由于模型能力上限未实际上传，但**不能静默丢信息**：

- 被能力上限挤掉的人物 / 场景 / 道具图片，若有对应资产文字 Prompt，则自动把该对象文字 Prompt 加入本次视频文本输入作为降级补偿。
- 这个“超限降级补偿”是“有图不用词”的明确例外：虽然本地有图，但本次请求实际上没有把该图传给模型，所以允许改用对应文字 Prompt。
- 该降级补偿不再受“基础设置是否允许无图文字回退”限制；它属于模型能力降级，不属于普通无图回退。
- 若被挤掉对象本身没有文字 Prompt，则只记录该对象因模型能力上限未传入，不凭空生成不存在的 Prompt。
- 画面提示词仍然永远不直接进入视频生成；这里补偿的只能是人物 / 场景 / 道具资产 Prompt。
- 必须在任务 / 日志中明确记录：模型上限、原计划参考图数量、实际上传哪些图、哪些图被降级、哪些对象改用了文字 Prompt。
- 禁止业务层随机删图、静默删图或假装模型已接收到全部参考图。

因此最终原则为：**能传图优先传图；超出能力上限时按稳定优先级保留最重要图片，被挤掉的资产图用其文字 Prompt 尽量补偿，并明确记录降级事实。**

```text
当前分镜 / VIDEOxx
↓
presetRefs
↓
先收集候选视觉输入：

+ 当前分镜引用的人物 / 场景 / 道具图片（若有）
```

所有模型能力降级必须显式记录，不能静默丢参考图。

## 15. 跟随音频：两个独立能力（已确认）

两个都关、单独开任意一个、两个同时开都允许。

### 15.1 生成阶段按音频时长约束

AI按真实音频总长规划分镜目标时长；provider 实际输出可以不同，不按单段强裁。

### 15.2 合成阶段按音频时长匹配

`自动倍率 = 视频实际总时长 ÷ 音频实际时长`

- >1.0x：加速
- =1.0x：原速
- <1.0x：允许慢放拉长

用户手动修改倍率时，直接覆盖自动推荐值，不叠乘。TTS / 音频主要用于时长和节奏，不默认混入最终视频音轨。

## 16. 画面图片生成（已确认）

画面图是独立于最终视频 Prompt 编译的一条生成链路。当前分镜引用对象逐个判断：对象有图就用图且不再注入该对象 Prompt；对象无图但有资产 Prompt 就直接使用对应资产 Prompt 补齐；对象既无图也无 Prompt 则不凭空伪造；最后叠加当前分镜画面提示词，交给当前有效图片模型生成画面图片。

### 16.1 无图文字回退不受“基础设置”控制

```text
画面图生成：
对象有图 → 用图
对象无图但有Prompt → 用Prompt补齐
不看基础设置开关

最终视频生成：
对象有图 → 用图，不用该对象Prompt
对象无图 → 是否使用该对象Prompt，由基础设置决定
```

### 16.2 批量“画面图”的执行范围

批量操作里的“画面图”只处理实际存在画面提示词的分镜。没有画面提示词的分镜，不因为批量按钮而凭空生成画面图。

## 17. 批量操作、任务与取消操作（已确认）

批量操作固定：人物场景图、画面图、生视频、重试、合并。

`AI推理 = 生成 Prompt / 规则`  
`批量操作 = 实际消耗模型资源`

重试支持用户勾选小说，并优先只重试失败阶段，避免重做已成功步骤。

### 17.1 每次批量操作形成独立 operation

每次实际批量任务形成一组独立 operation，用来关联这一次选中的小说、分镜、任务类型、队列任务和后续链路。

### 17.2 顶部“取消操作”只取消当前这一次 operation

点击顶部 `取消操作` 只针对当前这一次正在执行的批量 operation，不是一键停止整个作品。不会影响之前已经完成的媒体 / Prompt、其它 operation、与本次 operation 无关的任务、其它30本作品文档、已经成功保存的原始结果。

### 17.3 不伪造 provider 撤销能力

- 队列中尚未提交 provider → 直接取消，不再提交。
- provider 支持真实 cancel API → 尝试真实取消并记录结果。
- provider 不支持取消 / 已不可撤销 → 显示“已请求取消 / 停止后续处理”，不能伪装为“已取消成功”。

供应商结果即使随后返回，也不能继续自动触发本次 operation 的下游合并 / 上传121。

### 17.4 已完成结果不回滚删除

取消是停止继续执行，不是撤销历史结果。已成功结果保留，除非用户之后主动删除或重生成。

## 18. 小说列表“一行一本小说”的状态体系（已确认）

采用 **主状态 + 当前阶段 + 辅助标记**，不把十几个细碎步骤都塞成主状态。

### 18.1 主状态

| 主状态 | 建议颜色 | 含义 |
|---|---|---|
| 待开始 | 灰 | 尚未进入实际生产 |
| 处理中 | 蓝 | 当前有 AI / 图片 / VIDEO / 合并等任务进行中 |
| 异常 | 红 | 当前小说存在真实失败 / 阻塞，需要用户处理 |
| 待上传 | 青 / 蓝绿 | 媒体生产与合并已完成，等待上传121 |
| 上传中 | 蓝 | 正在执行121上传 / 提交 |
| 已完成 | 绿 | 121 已得到真实确认，整本流程真正完成 |
| 已取消 | 灰 | 当前这次相关 operation 已停止，不代表删除历史结果 |

### 18.2 当前阶段作为副文字展示

例如：`[处理中] AI推理中`、`[处理中] 视频 3/6`、`[处理中] 合并中`、`[待上传] 视频已合并`、`[上传中] 121提交中`、`[已完成] 121已确认`。

### 18.3 “已手调”是辅助标记，不抢主状态

用户手动改过 Prompt、分镜、引擎 override、素材等时，可显示紫色 `[已手调]`。它不是主状态。

### 18.4 异常优先级最高

若一本书同时存在“已手调”和真实失败，主状态必须显示 `[异常] [已手调]`。异常应给出真实阶段 / 对象，例如 `VIDEO04 生成失败`、`画面图02失败`、`121回读未确认`。

### 18.5 红色只用于真实异常

禁止“处理完成”却弹红色、成功状态长期以错误红色挂在列表、两行重复成功提示等表现。正常成功提示短暂反馈后消失；列表长期保留业务状态。

### 18.6 “已完成”必须代表真的完成

只有121真正确认成功后才进入 `已完成`。不能把 healthy、task_id、accepted_pending、queued/running、仅HTTP成功等当作整本“已完成”。

## 19. 合并（严格模式已确认）

### 19.1 基础合并规则

- 按分镜 / VIDEO 顺序合并。
- **每个分镜只读取该分镜当前“主框”的视频版本。**
- 候选框中的历史视频不会自动参加合并。
- 使用各主框 VIDEO 的实际时长。
- 可应用自动音频倍率或用户手动倍率。
- 某分镜主框切换或重新生成后，旧合并结果失效，可重新合并。
- 单分镜原始 VIDEO / 候选版本不因重新合并删除；但被第9.4规则正式淘汰的旧候选会执行物理清理。

### 19.2 任何“应该存在”的 VIDEO 失败 / 缺失，都阻止合并

采用严格模式，不允许自动跳过失败片段。

例如：

```text
VIDEO01 成功
VIDEO02 成功
VIDEO03 失败
VIDEO04 成功
```

此时点击合并：

```text
阻止合并
↓
提示：VIDEO03 尚未成功，请先重试后再合并
```

禁止系统偷偷变成：

```text
VIDEO01 + VIDEO02 + VIDEO04
```

用户可通过重试只重试失败阶段 / VIDEO03，成功后重新合并。

### 19.3 只有用户明确删除分镜，才从最终合并序列移除

“生成失败 / 尚未生成 / provider未返回”不等于“删除分镜”。只要该分镜仍属于当前有效分镜列表，就必须有对应成功 VIDEO 才允许合并。

如果用户主动执行“删除分镜03”并确认，那么新的有效序列才变成：

```text
分镜01 / VIDEO01
分镜02 / VIDEO02
分镜04 / VIDEO04
```

因此锁定：**失败片段不能自动跳过；缺失片段不能自动忽略；只有显式删除才改变有效合并序列。**

### 19.4 最终合并视频采用“当前最终版本 + 后台历史”（已确认）

同一本书重新合并后：

- 前台只需要明确一个“当前最终视频”。
- 新合并成功后，新结果成为当前最终视频。
- 旧合并结果可在后台保留历史记录用于追溯，不再作为默认当前版本。
- 上传121永远使用**当前被选中的有效最终视频**，不强制等于生成时间最新版本。
- 对外上传名称仍按第20章使用 `{bookId}.mp4`。

这里必须与“单分镜 1 主框 + 4 候选框”区分：前者是**整本书最终合并结果版本**，后者是**每一个分镜自己的 VIDEO 候选版本**。

### 19.5 最终合并历史保留数量（已确认）

每本小说最多保留 3 个完整合并视频实体：`当前最终视频 1 个 + 最近历史 2 个`。

重新合并成功时：

1. 新合并结果成为新的当前最终视频。
2. 上一个当前最终视频进入历史集合。
3. 历史集合只保留最近 2 个完整视频实体。
4. 若因此产生第 3 个历史版本，则删除最老历史视频实体。
5. 被清理的旧历史可保留轻量日志 / 元数据，例如合并版本ID、生成时间、参与的各分镜主框版本ID、删除状态，但不再保留可播放实体。
6. 对象存储删除失败时记录清理失败并进入可重试清理，不能伪装成成功。
7. 上传121永远只读取当前被选中的“当前最终视频”，历史版本不会在未切换为当前前自动用于发布。

例如：

```text
重新合并得到 Final-V4
↓
当前：Final-V4
历史：Final-V3、Final-V2
Final-V1：删除视频实体，只留必要日志 / 元数据
```

因此完整合并视频不会无限堆积，同时仍保留两个最近版本用于回看 / 追溯。

### 19.6 历史最终视频允许“设为当前”（已确认）

最终视频区域采用“当前最终视频主框 + 历史版本入口”的交互：

```text
最终视频主框                 [历史版本 2]
┌─────────────────────┐
│ 当前最终视频 Final-V4 │
└─────────────────────┘
```

点击 `历史版本` 后打开右侧 Drawer，最多展示当前保留的 2 个历史完整视频，可查看版本、生成时间、时长，并支持：`预览 / 设为当前`。

用户点击某个历史版本“设为当前”时：

- 不重新合并、不重新编码视频。
- 只切换当前最终视频指针，让该历史实体成为当前最终视频。
- 原当前最终视频回到历史集合；现有完整视频实体总数仍保持最多 3 个。
- 切换动作本身不删除任何仍处于这 3 个保留实体中的视频。
- “当前最终视频”是用户选择状态，不等同于生成时间最新版本。
- 后续下载 / 预览 / 上传121都以切换后的当前最终视频为准。
- 上传121对外文件名仍然固定为 `{bookId}.mp4`，不会把内部历史版本号暴露给121。

例如：

```text
切换前：
当前 Final-V4
历史 Final-V3、Final-V2

用户把 Final-V2 设为当前
↓
当前 Final-V2
历史 Final-V4、Final-V3
```

之后如果再执行一次新的真实合并，则按第19.5节的保留数量规则重新整理“当前1个 + 历史2个”。

仍待实现层确定：内部对象存储 key / 数据库版本标识的具体命名格式；该命名属于实现细节，不影响用户选择当前版本或121的 `{bookId}.mp4` 对外命名。

## 20. 上传网络（121）

顶部按钮名称为 `上传网络`，位于水货“导出剪映”对应位置；发布配置在 `引擎配置 → 发布统一`。发布统一必须按第6.3节保留“版本对应配置档 / 保存网站提交配置 / 环境自检 / 同步网站配置档 / 同步网站风格类型”。

正文来源按第4章：

- 不改文 → `sourceContentCaptured`
- 改文 → 用户确认后的改文版本

### 20.1 121 上传视频 / 文本统一使用 bookId 命名（已确认）

121 对外上传时，不使用书名、个人作品文档名或用户重命名后的名称作为业务匹配键，而统一使用小说的 `bookId`。

当121接口实际以文件形式接收时，文件名固定为：

```text
视频：{bookId}.mp4
文本：{bookId}.txt
```

例如：

```text
bookId = 123456
↓
123456.mp4
123456.txt
```

这样视频和正文天然以同一个小说 ID 配对。个人作品重命名、小说书名变化、中文/特殊字符都不能改变121上传使用的业务 ID。

### 20.2 文件名与正文内容选择是两套独立规则

无论 `改文 / 不改文` 如何选择，121文本的对外文件名都仍然是 `{bookId}.txt`；变化的是这个 TXT 文件里的正文内容：

```text
不改文 → 123456.txt 内写 sourceContentCaptured
改文   → 123456.txt 内写用户确认后的改文版本
```

视频同理：121 使用当前被选中的有效最终合并视频，但对外上传文件名统一为 `{bookId}.mp4`。

### 20.3 `上传网络` 是下拉按钮：提交选中 / 提交全部（已确认）

点击顶部 `上传网络` 后向下展开两个操作：

```text
上传网络 ▼
├─ 提交选中
└─ 提交全部
```

#### 提交选中

- 执行范围 = 当前小说列表中明确勾选的小说。
- 例如当前作品30本、勾选8本，则只把这8本放入本次121发布候选集合。
- 没有勾选任何小说时，`提交选中` 阻止执行并提示先选择小说。
- 未勾选小说不受影响。

#### 提交全部

- 执行范围 = 当前批量工厂作品文档中的全部小说（通常最多30本）。
- 不要求用户事先手动全选。
- `提交全部` 是明确的全量动作，因此不能再把“无勾选”解释为错误，也不能和“提交选中”混为同一语义。

### 20.4 两种提交方式都采用“部分通过模式”（已确认）

无论用户选择 `提交选中` 还是 `提交全部`，系统先逐本做上传前就绪校验，然后采用部分通过模式：

```text
本次候选 8 本
├─ 5 本就绪 → 正常进入121提交
└─ 3 本未就绪 → 跳过，不提交，并逐本显示原因
```

规则：

- 一部分小说未就绪，不得把其它已经就绪的小说全部卡死。
- 就绪小说继续提交，未就绪小说单独跳过。
- 被跳过小说必须显示明确原因，例如“尚无当前最终视频 / 发布正文不可用 / 发布配置缺失”等。
- 跳过不等于失败提交，更不能标记为 `accepted_pending / submitted / 已完成`。
- 只有真正发起121请求的小说才进入 `上传中` 等发布状态。
- 本次操作结束后应汇总：候选总数、实际提交数、跳过数，以及每本跳过原因。

因此新版用户心智为：**上传网络 → 明确选择“提交选中”或“提交全部” → 逐本校验 → 就绪的继续提交、未就绪的单独跳过。**

### 20.5 上传网络前逐本基础就绪校验：4项（已确认）

每本进入121真实提交前，至少必须通过以下4项基础校验：

1. `bookId` 存在且有效：必须能作为该小说在121侧的稳定身份与 `{bookId}.mp4 / {bookId}.txt` 命名依据。
2. 当前最终视频存在且文件可用：必须已经有“当前最终视频”指针，对应视频实体仍存在、未被清理且能够被发布链路读取；用户从历史版本“设为当前”后的版本同样有效。
3. 本次发布正文可正常生成且非空：不改文时能够得到 `sourceContentCaptured`；改文时能够得到用户确认后的改文版本；不能生成有效正文或结果为空时，该书跳过。
4. 121发布配置 / 登录会话 / 提交通道当前可用：当前作品/账号所需发布配置完整，121登录或授权会话有效，真实提交桥接 / API 通道处于可用状态。共享会话或通道若整体不可用，应把对应候选逐本标记为未就绪并显示同一真实原因，而不是继续伪提交。

只有4项全部通过，这一本小说才允许真正发起121请求。任意一项未通过时，只跳过这一书并给出对应原因，其它通过校验的小说继续按“部分通过模式”提交。

基础校验只决定“能否开始真实提交”，不代表121已经接受或发布成功；后续 `accepted_pending / queued / running / submitted / confirmed` 等状态必须根据真实121响应与回读结果另外判断。

### 20.6 提交后真实状态与“已完成”判定（已确认）

121提交后的状态必须区分“请求已被接收”与“121已真实确认成功”。不能因为接口请求看起来成功，就提前结束整本流程。

```text
HTTP 2xx / 请求返回成功
或 task_id
或 accepted_pending
↓
只代表请求已被接收 / 已进入处理链路
主状态仍为：上传中（或待确认）

queued / running
↓
仍为：上传中

submitted 但尚未完成真实回读确认
↓
仍不能进入“已完成”

121真实回读确认该 bookId 已提交成功
↓
主状态：已完成
```

硬规则：

- `HTTP 200/2xx` 只能证明这一层请求成功返回，不能证明121最终业务已完成。
- `task_id` 只是任务身份，不是成功凭证。
- `accepted_pending` 表示已接受、等待后续处理，不得解释成真实提交成功。
- `queued / running` 明确属于处理中状态，继续显示 `上传中`。
- `submitted` 若只是桥接层 / 任务层返回的状态，但尚未完成121真实回读确认，也不能把整本小说标成 `已完成`。
- 只有从121真实状态 / 书单 / 提交记录等可信回读链路，确认当前 `bookId` 的本次发布已经成功，才允许进入绿色 `已完成`。
- “已完成”是整本工作流终态，必须对应121真实确认，不得由本地推测、合同测试、健康检查或中间任务状态替代。
- 若真实回读明确返回失败、拒绝、未授权或其它业务错误，则应进入真实异常处理，不得保留虚假的完成状态。

因此状态链锁定为：**发起请求 → 上传中 / 待确认 → 121真实回读确认 → 已完成。**

### 20.7 回读超时、防重复提交与重新提交（已确认）

一旦某本小说的本次121发布已经获得 `task_id / accepted_pending / queued / running / submitted但待真实确认` 等任何“已有在途任务”的证据，系统必须把这次发布视为一个仍需追踪的 `publicationAttempt`，并优先回读该原任务，禁止因为等待时间过长、页面刷新、网络抖动或用户再次点击批量上传而自动重复提交同一本书。

规则：

- 同一个 `bookId` 在存在未终结的121发布尝试时，默认只做状态回读，不再次上传 `{bookId}.mp4 / {bookId}.txt`。
- 自动轮询、页面刷新、任务恢复、批量“提交全部”再次扫到该书时，都必须先识别已有在途 attempt，避免产生第二份重复提交。
- 超过回读超时阈值仍无法得到121最终结果时，主状态进入真实异常，例如：`[异常] 121回读超时`；但这不代表原任务失败，更不能自动创建新提交。
- 超时后提供 `重新检查`。`重新检查` 只重新查询原 attempt / 原 task_id / 原 bookId 的真实状态，不发送新的上传请求。
- 只有可信回读明确确认原任务 `失败 / 拒绝 / 不存在 / 已失效`，或系统通过真实渠道确认不存在仍在处理的旧任务后，才允许用户执行真正的 `重新提交`。
- 如果原任务在“回读超时”之后迟到地被121确认成功，应立即把该书更新为 `已完成`，并继续阻止重复提交。
- 真正重新提交时应创建新的 publication attempt，并保留与旧 attempt 的关联日志；旧 attempt 的失败/失效证据不能被覆盖。
- 不允许把“本地超时”“查询接口暂时失败”“浏览器桥接断开”当作“原121任务已经失败”的证据。

因此锁定：**先防重复，只回读；超时转异常但不自动重提；确认原任务已失败/不存在后，才允许重新提交。**

### 20.8 回读轮询与超时默认参数（已确认）

默认参数：

```text
121状态回读间隔：10秒
最长自动等待：10分钟
```

规则：

- 从某次 `publicationAttempt` 进入需要回读确认的状态开始，后端默认每10秒查询一次121真实状态。
- 在10分钟自动等待窗口内，只要得到最终成功或明确失败 / 拒绝 / 不存在 / 已失效，就立即结束本轮自动轮询并按真实结果更新状态。
- 10分钟内始终得不到最终结果，则停止自动轮询，并把该书标记为 `[异常] 121回读超时`。
- 超时后保留 `重新检查`；该动作仍只检查原 attempt，不自动发起新的上传。
- 这两个参数必须由后端配置统一管理，前端只展示状态，不把 `10秒 / 10分钟` 写死在UI逻辑里。
- 后台以后可以根据121真实处理速度调整轮询间隔与超时阈值，而不需要改前端代码。
- 参数调整只影响等待策略，不改变第20.6、20.7节的业务真值：未真实确认前不能标记完成，回读超时也不能等同于提交失败。

因此默认策略锁定为：**10秒轮询一次，最长自动等待10分钟；超时停止自动轮询并转异常，允许手动重新检查；参数后端可配置。**

若121真实协议最终不是“上传物理文件”，而是通过表单字段 / 浏览器桥接 / API payload 传输，也仍应以 `bookId` 作为小说身份与配对依据；具体 transport 字段名称以实际接口为准，不能凭空猜测。

这一条是新版设计协议。当前尚未拿到足够代码证据证明旧小说获取的每一条121实现路径已经全部使用同样文件命名，因此实现阶段必须对照小说获取现有真实提交链路复核，而不能因为设计已锁定就假定旧代码已经符合。

上传继续复用小说获取已经存在的121提交思路；仍需确认真实 API / 浏览器桥接，以及“版本对应配置档”的具体字段映射 / 同步覆盖策略。

## 21. 小说获取 → 批量工厂来源数据

小说获取入口不重新抓小说；它至少关联：sourceTaskId、bookId、书名、平台、本次选择的 sourceVariant、sourceContentCaptured、metadata，并把用户已选择或改写后的正文直接传入批量工厂。手动入口则按“内容截取”获得并保存正文。

手动新建批量入口允许用户按小说获取的书单输入协议一次填写任意数量的书籍信息：书城/平台、输入格式、列预设或自定义列顺序以及多行清单。系统解析得到 `bookId`、书名、男女频、标签、评级、推荐理由等元数据，并为这些书取得原始正文；之后和小说获取入口一样创建一个批量工厂作品。手动入口不接受手工粘贴或上传正文；需要改写正文时使用小说获取入口。

## 22. 当前 v88 Git 现状与新版冲突

- `BatchFactoryPageV11.jsx` 是兼容入口；实际旧 V11 UI 在 `batch-factory-v11/BatchFactoryV11UiPage.jsx` 一带。
- 旧工作台仍有状态筛选、拖拽/缩放/隐藏、Hook/Director、visualPrompt 等旧逻辑；这些是现状，不代表新版继续沿用。

- 现有 scoped settings 已有 `系统默认 → 批次 → 当前小说 → 单VIDEO` override 的旧基础；新版已确认继续保留单分镜 / 单VIDEO override 能力，但 UI 和字段必须按新版规则收口。

- 水货“片段库”已有主框 + 候选框交互，新版批量工厂应对标其用户心智，但数据身份仍必须按“每本小说 → 多分镜 → 每分镜多视频版本”独立管理。

## 23. 已废弃 / 被新规则覆盖的旧思维

- 大一统“生产统一设置” → 拆成引擎配置 + AI推理。
- 画面提示词直接进视频 Prompt → 废弃。
- 有对象图仍重复注入对象 Prompt → 废弃；仅“模型参考图超限且该图片未实际传给模型”时允许按第13.1节文字补偿。
- 音频比视频长不允许慢放 → 废弃。
- 状态中心 + 自由布局是主页面核心 → 改为水货式一行一本小说。
- 只支持失败 VIDEO 重试 → 改为支持选书并按失败阶段重试。
- Intake 后必须手动创建批次 → 废弃；但批量工厂保留“新建批量”手动导入入口，允许按小说获取完整书单输入协议一次填写任意数量的书籍元数据，并与小说获取导入共用同一生产链路。
- 原文直转 / 爆款开头作为两个互斥大生产模式 → 废弃。
- 固定开头=单个视频时 AI 只生成一个分镜 Prompt → 废弃。
- 固定开头=多个视频需要另外填写数量 / 停止数量 → 废弃。
- 单分镜不能独立调整引擎配置 → 废弃。
- 画面图无图文字回退受基础设置控制 → 废弃。
- 取消操作 = 停掉整个作品所有任务 → 废弃。

- 成功 / 处理完成使用红色长期展示 → 废弃；红色只表示真实异常。

- 单分镜重新生成后直接覆盖并丢失旧成功 VIDEO → 废弃；现在每分镜保留主框 + 4 个候选版本，合并只读取主框。

- 单分镜候选版本无限堆积 → 废弃；现在只保留主框 + 最近4个候选，候选满后自动淘汰最老候选。

- 整本最终合并视频历史无限保留 → 废弃；现在只保留当前1个 + 最近2个历史完整视频实体，更老版本删除实体只留必要日志。
- 整本最终合并视频只能使用时间上最新版本 → 废弃；历史完整视频可由用户直接“设为当前”，121跟随当前指针发布。
- 参考图超过模型上限就整批阻塞，或业务层静默随机丢图 → 废弃；现在按画面图 > 人物图 > 场景图 > 道具图稳定降级，并对被挤掉的资产图使用对应文字 Prompt 补偿。
- 顶部单一“上传121”按钮直接执行 / 无勾选就禁止一切上传 → 废弃；现在顶部按钮为 `上传网络` 下拉菜单，显式提供 `提交选中 / 提交全部`。
- 任意一本未就绪就阻塞整次121批量提交 → 废弃；现在两种提交方式均采用部分通过模式。
- 未经过 `bookId / 当前最终视频 / 发布正文 / 121发布配置与通道` 校验就直接尝试提交 → 废弃；现在每本必须先通过4项基础就绪校验。
- 把 `HTTP 200/2xx / task_id / accepted_pending / queued / running / 未回读确认的 submitted` 当作整本已完成 → 废弃；只有121真实回读确认当前 `bookId` 成功后才能进入 `已完成`。
- 回读超时或网络异常后自动再次上传同一 `bookId` → 废弃；现在先追踪原 publication attempt，超时只转异常并重新检查，只有确认原任务失败/不存在后才允许重新提交。
- 把121回读频率和超时阈值写死在前端 → 废弃；默认10秒轮询、10分钟超时，但由后端配置统一管理。
- 把“发布统一”收窄成只有改文开关和通道状态、移除“版本对应配置档 / 网站配置同步 / 风格同步 / 环境自检” → 废弃；这些能力必须继续保留在发布统一。

### 5.3 单书阶段操作、重试与重新生成（已确认）

每本小说在最右“操作”列独立提供：`刷新 / 生成文案 / 生成图片 / 生成视频 / 重试`。普通生成坚持“不覆盖已有成果”：已有与当前文本、配置匹配的 Director 文案不重复生成；已有资产主图不重复生图；已有同一 Director revision 的 VIDEO 不重复提交。

`重试`只识别该书最后失败阶段（文案、图片、VIDEO）并只重跑它，不能把其他成功阶段重新执行。刷新只回读当前书状态，不创建任务。

用户主动改动资产、画面提示词或视频提示词后，在对应居中弹窗内使用“重新生成”：

- 人物场景预设：资产可编辑 Prompt、保存、生成图片、重生图；顶部可重新生成资产或重试失败资产。手动资产与手动 Prompt 不被普通文案生成覆盖。
- 提示词：可重新生成文案或重试文案；手动保存的单 VIDEO Prompt 继续是单 VIDEO override，只有用户明确允许时才用 AI 结果覆盖。
- VIDEO / 片段库：可对当前 VIDEO 重新生成或重试失败任务。重新生成只新增候选版本，原主版本不自动替换，用户在片段库选择主版本。

图片、文案、视频的提交必须根据当前书生效配置检查文本 / 图片 / 视频模型和对应模块开关。服务端保存书级阶段记录，并以此决定跳过、强制重新生成和最后失败步骤；浏览器不伪造成功或可用状态。
