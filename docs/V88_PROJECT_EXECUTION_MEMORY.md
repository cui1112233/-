# V88 项目执行记忆（跨对话统一规则）

> 目的：避免后续不同对话框把 V88、Git、公网、Docker 的关系搞混，导致修复只存在公网、后续迭代又被覆盖或找不回来。

## 0. 文档优先级

后续任何 GPT / Codex / 自动化在执行 V88 任务前，按以下顺序读取：

1. `AGENTS.md`：绝对执行规则与角色边界。
2. `docs/V88_CURRENT_STATE.md`：当前实时状态，包括 Git 主线、公网运行 SHA、部署方式、回滚点。
3. 本文件：长期稳定的架构约定与项目记忆。
4. `obj`：历史日志，只用于追溯过去发生过什么；历史条目不得覆盖当前状态和现行规则。

## 1. 唯一正式源码

- GitHub 仓库：`cui1112233/-`
- 当前唯一维护主线：`v88`
- `v88` 将作为后续总分支，并计划最终承担 master/main 的角色。
- 所有新功能、Bug 修复、UI 小改、提示词、部署脚本、数据库迁移，都必须先写进 Git 的 V88 lineage。
- 旧 V78、历史 release、旧 feature/fix/integrate/diag/design 分支只作为参考源，不再作为维护目标。
- 禁止粗暴把历史分支整体 merge 回 `v88`；如需回迁，只迁移经过审计的最小必要变更。

## 2. 公网与 Git 的关系

- Git `v88` = 唯一源码真相（Source of Truth）。
- ECS 公网 = `v88` 的运行副本，不是开发源。
- 正常流程严禁“只改公网容器/服务器文件，Git 不记录”。
- 即使发生紧急线上止血，只要动过公网代码/配置，也必须立即把同样改动回写到 Git `v88`；没有回写 Git，就不能算任务完成。
- 后续任何对话在动公网前，应先确认当前 Git `v88` 最新 SHA，再基于该 SHA 工作，禁止拿旧 `app.js`、旧热修复包、旧镜像整份覆盖当前 V88。
- 公网运行 SHA 可以在紧急恢复期间短暂落后于 `v88` HEAD，但必须在 `docs/V88_CURRENT_STATE.md` 明确记录，不允许让使用者误以为 Git HEAD 就是公网版本。

## 3. 多 GPT / 多会话协作

固定三类角色：

- **开发工人（Development worker）**：从最新 `v88` 建独立功能/修复分支，只负责开发、测试、提交，不允许发布公网，不允许 force/update `v88`。
- **发布总控（Release coordinator）**：唯一负责把已验收改动合入 `v88`、发布公网、记录运行 SHA 和回滚 SHA。
- **紧急恢复（Emergency recovery）**：只负责恢复最后一个已验证版本，不顺便开发新功能。

因此多个网页版 GPT 可以并行，但不能共同直接修改/发布同一个 `v88`。每个功能聊天最终交付：分支名、commit SHA、测试结果、影响文件，由总控统一合入和发布。

## 4. 默认开发流程

标准流程固定为：

`最新 v88 -> 独立功能/修复分支 -> 测试 -> 总控验收 -> 合入 v88 -> 记录 commit SHA -> 再发布/同步公网`

禁止把以下方式当成正常开发流程：

`直接改公网 -> 验证能用 -> 结束`

也禁止：

`多个聊天同时直接写 v88 -> 各自发布 -> 谁最后执行谁覆盖`

## 5. 目标生产架构 A

用户确认采用 A 架构：主网站逐步摆脱 Docker Node/Nginx 作为可用性前置条件，但 Docker 可继续承载确实适合容器隔离的组件。

目标拓扑：

`Internet -> Host Nginx -> Host Node / Host Go -> MySQL / Redis / TOS`

以及：

`Host Node/Go -> Docker Browser Worker（视频管理系统/121 浏览器执行等隔离型服务）`

关键原则：

- Host Nginx 与主站 Host Node 必须随 ECS 开机自动启动。
- Browser Worker、Docker 网络或旧 Docker Node 出故障时，主站入口仍必须能打开。
- Worker 功能故障只能影响对应 Worker 功能，不能拖垮整个公网入口。
- MySQL/Redis 在迁移期是否继续 Docker 化不是当前前置条件，以稳定和数据安全优先。

## 6. 增量发布规则

推荐目标：

`Git v88 -> ECS 获取指定 commit -> 按变更类型增量构建 -> 重启对应服务 -> 健康检查 -> 记录公网运行 SHA`

- 仅前端/CSS/文案改动：只同步代码 + 构建前端 + reload/restart 必要服务。
- Node 业务代码改动：同步代码 + 安装依赖（仅依赖变化时）+ 重启 Node。
- Go API 改动：同步代码 + `go build` + 重启 Go 服务。
- Goose migration 改动：部署时执行对应数据库迁移。
- Browser Worker 改动：只更新/重启 Worker；依赖变化时再安装依赖。
- MySQL、Redis、TOS 等持久化基础设施不应因普通 UI/业务小改而重装或重建。

目标是让小改动尽量在几十秒到 1～2 分钟内进入公网，而不是每次都重建完整 Docker 镜像。

## 7. Docker 的定位

- “日常发布不用 Docker”不等于“服务器完全不能使用 Docker”。
- 用户本地 Mac/Windows 的 Docker 不应成为生产运行前置条件；生产容器如果存在，运行在 ECS 上，用户电脑关机不应影响公网。
- 现有 MySQL、Redis、Playwright/Browser Worker 等如果当前稳定运行，可以先继续保留。
- 主站应用代码发布优先采用 Git -> ECS 直部署。
- 不应为了一个按钮、状态文案、CSS 等小改重新构建整套 Docker 镜像。
- 若未来确实需要容器化发布，必须从 Git `v88` 的明确 commit 构建，不能从公网现状反向制作镜像。

## 8. 公网版本可追溯要求

每次公网发布后必须能回答：

- 当前公网运行的是哪个 Git SHA？
- 这个 SHA 是否属于 `v88` lineage？
- Git `v88` 当前 HEAD 是什么？
- 上一个可回滚 SHA 是什么？
- 当前 deploy mode 是什么？

推荐保留：

- `/opt/qiantie/v88`：Git 工作副本/发布工作区。
- release 目录：按 SHA 保存可回滚版本。
- current/previous stable SHA 状态文件。
- `/api/build-info` 返回运行 SHA 与 deploy mode。
- 自动健康检查与失败回滚。

## 9. 现有技术栈约定

- API / 后端：Go（Golang），编译为二进制。
- 管理端：React + Ant Design。
- 用户端：React + Ant Design。
- 数据库：MySQL。
- 数据库迁移：Goose。
- 队列/锁/非关系型数据：Redis。
- 对象存储：TOS。
- 系统提示词：后端保存模板并在运行时替换真实提示词。
- 传统部署目标仍可使用 Go embed 打包前端资源；在当前混合迁移阶段，允许 Node/Go 并存，但新功能最终向 V88 统一架构收口。

## 11. 后续对话执行前检查

任何后续对话在执行 V88 开发/发布前，应先确认：

1. `docs/V88_CURRENT_STATE.md` 是否仍是最新状态。
2. 当前 Git `v88` 最新 SHA。
3. 当前任务是否在从最新 `v88` 创建的独立分支上。
4. 本任务改动是否已经写进 Git，而不是只存在公网。
5. 是否会用旧文件/旧热修复覆盖当前 V88。
6. 当前会话是否属于发布总控；如果不是，不得发布。
7. 小改是否可以走增量部署，而不是完整 Docker 构建。
8. 发布完成后是否记录运行 SHA、回滚 SHA并做健康检查。

## 12. 核心原则（一句话）

**Git `v88` 是唯一正式源码；普通 GPT 只在独立分支开发；发布总控统一合入和发布；公网只是可追溯运行副本；主站最终由 Host Nginx + Host Node/Go 提供，Docker 只保留隔离型组件。**
