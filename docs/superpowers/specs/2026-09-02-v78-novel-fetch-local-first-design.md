# V78 小说获取：本地优先存储、云端继续生产与本地 121 上传设计

日期：2026-09-02

状态：设计已在聊天中确认，等待用户对本文件最终复核

基线分支：`feat/v78-novel-fetch-v2-completion`

基线 SHA：`fc1f5a96364518f0f14073fd5195363ef0e15a77`

## 1. 目标

本次改造解决三个问题：

1. 小说获取产生大量原文、AI1、AI3、AI5 等正文后，不让服务器长期积累完整正文。
2. 用户电脑关机时，选择“云端继续”仍可继续抓原文和完成 AI1 / AI3 / AI5；电脑重新上线后再同步并继续 121 上传。
3. 121 登录入口保持在“小说获取”网页里，但浏览器执行和登录会话迁移到用户电脑的“一战晟铭本地执行器”，正常使用时不弹浏览器窗口。

核心原则：**历史记录与正文内容彻底分离。历史可以长期保存，完整正文按用户设置自动清理。**

## 2. 已确认的用户体验

### 2.1 正常生产

用户仍在“小说获取”页面完成操作：

```text
输入小说 / 导入任务
→ 选择原文 / AI1 / AI3 / AI5
→ 开始生产
→ 云端按任务继续处理
→ 页面显示进度和历史
→ 本地执行器在线时同步正文
→ 需要时自动上传 121
```

用户不需要为了这套架构额外打开本地执行器界面。

### 2.2 默认不生成真实 TXT

原文、AI1、AI3、AI5 默认保存为“内部正文数据”，不自动在用户电脑目录里生成大量 `.txt` 文件。

只有用户主动点击“下载/导出”时，才创建真实 TXT，例如：

```text
原文.txt
AI1.txt
AI3.txt
AI5.txt
```

因此，批量生产几千本、几万本文案时，不会在用户可见目录里堆出同等数量的 TXT 文件。

### 2.3 用户手改后的 TXT 优先

如果用户已经把某个版本导出为真实文件，例如 `AI3.txt`，并手动修改过：

- 只要该导出文件仍存在，121 上传优先读取该真实文件的当前内容。
- 系统不得用内部旧正文静默覆盖用户手改文件。
- 如果用户重新生成 AI3，而本地已有用户修改过的 `AI3.txt`，新结果不得直接覆盖该文件。
- 重新生成结果应保留为新的内部版本；若用户再次导出，可用带时间或版本标记的新文件名。

如果已导出的真实文件后来被用户删除：

- 若内部正文仍存在，则回退到内部正文，并在界面标记“本地导出文件已不存在”。
- 若内部正文也已清理，但云端临时正文仍存在，可恢复到本地内部存储。
- 若两边都不存在，则历史仍保留，但正文状态显示“正文已清理”，需要重新抓取或重新生成。

## 3. 当前源码兼容事实

当前 121 上传逻辑已经证明“不需要硬盘上真实存在一个 `书籍ID.txt` 文件”也能上传：

- 上传字段是 `files[]`。
- MIME 类型是 `text/plain`。
- 正文以 UTF-8 放入 multipart 文件体。
- 121 根据上传文件名识别书号。
- 上传文件名必须是 `书籍ID.txt`，不能把 `AI1`、`AI3` 等版本名混进文件名。

对应现有代码路径：

- `lib/target-upload.js`
- `routes/novel-fetch-upload.js`
- `services/121-browser-worker/src/actions.js`

因此新架构继续保持相同协议：

```text
本地内部版本：AI3
或真实文件：AI3.txt
          ↓
读取正文内容
          ↓
上传时临时命名为：<bookId>.txt
          ↓
multipart/form-data → files[] → text/plain → UTF-8
```

上传时只是临时构造 multipart 文件对象，不需要额外复制一个 `书籍ID.txt` 到磁盘。

## 4. 总体架构

采用“云端生产 + 本地执行器 + 临时正文”的方案。

```text
一战晟铭网页
│
├─ 小说获取 UI
├─ 历史记录 / 设置 / 任务状态
│
├─ 云端服务
│  ├─ 用户账号和权限
│  ├─ 任务调度
│  ├─ 原文抓取
│  ├─ AI1 / AI3 / AI5 生产
│  ├─ 历史元数据
│  ├─ 临时正文存储
│  └─ 清理策略
│
└─ 一战晟铭本地执行器
   ├─ 本地内部正文存储
   ├─ 导出 TXT 管理
   ├─ 设备绑定 / 在线状态
   ├─ 121 无头浏览器
   ├─ 121 登录会话
   └─ 121 自动上传
```

### 4.1 云端长期保存什么

长期保留轻量元数据，例如：

- 用户 ID
- 书籍 ID
- 书名
- 平台、男女频、风格
- 任务创建/完成时间
- 选择了哪些版本
- 原文 / AI1 / AI3 / AI5 是否完成
- 每个版本的字符数、摘要哈希、完成时间等轻量信息
- 121 是否上传成功
- 使用的 121 账号标识（不保存 121 密码）
- 任务状态、错误码、错误摘要
- 是否曾导出
- 云端正文是否仍存在、何时到期
- 本地正文是否已同步（仅状态，不上传用户文件内容作为历史）

### 4.2 云端不长期保存什么

以下完整内容受清理策略控制，不作为永久历史保存：

- 原文完整正文
- `originalRaw` 与清洗后的原文重复副本
- AI1 / AI3 / AI5 完整正文
- 其他完整改写版本
- 为 121 上传临时构造的 multipart / Base64 数据

当前工作台把 `meta + original + originalRaw + versions + logs` 放在同一个任务文档中的模式，需要拆成“元数据”和“正文对象”两层。

## 5. 正文存储模式

用户可以选择两种运行模式。

### 5.1 本地优先

目标：服务器不长期留下正文。

行为：

- 本地执行器在线时，云端抓取/AI 产生正文后尽快传给绑定设备。
- 本地执行器确认收到并校验后，云端正文副本可以立即进入可删除状态。
- 如果当前任务下一步必须依赖该正文且云端仍在处理，可以保留执行所需的短暂工作副本；任务完成或本地确认后删除。
- 如果电脑关机/执行器离线，任务在需要持久正文的节点暂停，不为了“继续生产”而把正文长期留在云端。

### 5.2 云端继续

目标：电脑关机后仍然完成原文 + AI1 / AI3 / AI5。

行为：

```text
电脑在线
→ 正常生产并同步本地

电脑离线
→ 云端继续抓原文
→ 云端继续生成 AI1 / AI3 / AI5
→ 完整正文暂存云端内部正文存储
→ 121 上传等待

电脑重新上线
→ 本地执行器同步缺失正文
→ 校验成功
→ 继续 121 上传
→ 云端正文按清理规则删除
```

原先讨论过的“云端正文固定最多 3 天”由新的统一清理设置替代：默认 7 天，可设 1～30 天，并受服务器空间保护规则约束。

## 6. 正文内部存储

“内部正文”不是“完全不占空间”。它仍是实际数据，只是不以用户可见 `.txt` 文件形式存在。

设计要求：

- 云端正文使用独立正文存储，不再把完整正文长期塞进历史元数据记录。
- 原文原则上只保留一份规范正文；避免同时永久保存 `originalRaw` 和几乎相同的 `original` 两个完整副本。
- 需要保留原始响应信息时，只保留必要摘要、哈希、字符数或短小诊断字段。
- 完整正文可采用压缩存储；压缩是内部实现细节，不改变下载和 121 上传内容。
- 本地执行器也使用内部正文存储，不需要自动生成 TXT。

## 7. 历史记录与正文生命周期

历史记录与正文完全独立。

即使完整正文已经删除，历史仍可显示：

```text
《某某小说》  767451...
✓ 原文
✓ AI1
✓ AI3
- AI5
121：已上传
完成时间：2026-09-02
正文：已清理
```

历史记录不依赖实体 TXT，也不依赖完整正文仍存在。

### 7.1 导航设置

设置入口放在现有导航栏的“设置”，不是在小说获取页面再做一套独立设置。

建议路径：

```text
设置
└─ 小说获取
   └─ 数据与清理
```

提供：

```text
历史记录
[立即清除历史记录]

正文自动清理
[7 天 ▼]
范围：1～30 天
```

默认：7 天。

**“立即清除历史记录”只删除历史元数据，不直接删除云端正文、本地内部正文或用户导出的 TXT。** 正文仍按自己的生命周期和安全条件清理，避免两个按钮的语义混在一起。

### 7.2 自动清理对象

达到清理时间后，删除的是完整正文内部数据：

- 原文正文
- AI1 正文
- AI3 正文
- AI5 正文
- 其他完整版本正文

保留历史元数据。

### 7.3 云端与本地一致清理

同一“正文自动清理”设置管理：

- 云端内部正文
- 本地执行器内部正文

但用户主动下载/导出的真实 TXT 永远不由系统自动删除。

### 7.4 清理安全条件与计时起点

普通定时清理不得删除仍然承担任务职责的正文。

以下状态不执行普通定时正文清理：

- 正在抓取或生成
- 等待后续 AI 处理
- 等待本地同步
- 等待 121 上传
- 121 上传失败且仍处于自动重试/待处理
- 人工转移正在进行

实现上，每个正文对象设置 `releasableAt`。只有在该正文已经不再被生产、同步、上传或转移依赖时才写入该时间。用户设置的 1～30 天从 `releasableAt` 开始计算，而不是简单按“正文生成时间”计算。

### 7.5 服务器容量保护

即使用户设置 30 天，也必须有服务器安全容量保护。

当临时正文存储达到预设安全阈值时：

1. 只从“可安全清理”的正文中选择。
2. 优先清理最旧正文。
3. 不删除历史记录。
4. 不删除用户电脑上已导出的 TXT。
5. 不清理仍在生产、同步、上传或等待人工处理的正文。
6. 页面明确记录“因空间保护提前清理”。

容量阈值必须是服务端配置，不允许单个普通用户关闭全局保护。

## 8. 121 登录与上传

### 8.1 登录入口保持在小说获取网页

用户操作保持：

```text
小说获取
→ 点击 121 账号
→ 网页弹出登录框
→ 输入账号密码
→ 登录成功
→ 页面显示：账号名 ● 在线
```

用户不需要先打开本地执行器的设置页登录 121。

### 8.2 浏览器执行迁移到本地

网页发起登录请求后：

```text
小说获取网页
→ 云端把登录任务路由到当前绑定设备
→ 本地执行器启动无头 Chromium
→ 完成 121 登录
→ 登录会话保存在该设备本地
→ 返回账号和状态
```

正常登录和上传使用无头浏览器：

- 不弹 Chrome 窗口。
- 不抢鼠标键盘。
- 浏览器按需启动，不要求 24 小时常驻。
- 登录 Cookie / storage state 保存在本地。
- 上传完成后可关闭浏览器实例，只保留会话数据。

只有 121 要求验证码、滑块、短信、人机验证等人工操作时，才弹出可见浏览器窗口。

人工验证完成后恢复无头模式。

### 8.3 会话隔离

同一台电脑只安装一个本地执行器，但 121 会话必须按“一战晟铭用户 + 设备”隔离。

例如：

```text
一战晟铭用户 A + 办公室电脑 → 121 张三
一战晟铭用户 B + 办公室电脑 → 121 李四
```

不得因为共用一个本地执行器而串用 121 会话。

121 登录会话不在不同电脑之间自动复制。

### 8.4 121 上传正文来源优先级

每次上传都重新解析正文来源，避免使用过期缓存：

1. 如果该版本存在用户导出的真实 TXT 且文件仍存在：读取真实文件当前内容。
2. 否则读取本地执行器内部正文。
3. 若本地没有，但云端临时正文仍存在：先同步到本地，再上传。
4. 若正文已全部清理：停止上传并提示重新抓取/生成。

无论来源是什么，真正发给 121 的临时上传文件名一律为：

```text
<bookId>.txt
```

## 9. 本地执行器生命周期

本地执行器采用：**开机自动启动 + 后台常驻 + 托盘图标**。

状态示例：

```text
● 在线
正在同步
正在上传
需要 121 验证
异常
```

用户可以主动退出执行器；退出后所有依赖本机的同步和 121 上传暂停。

电脑睡眠、关机或执行器退出时，本地无头浏览器不可能继续运行。

重新启动后：

- 自动连接云端。
- 拉取待同步正文。
- 恢复等待中的本地任务。
- 检查 121 会话。
- 继续待上传任务。

## 10. 设备绑定与多设备

### 10.1 绑定方式

不要求用户在本地执行器里再次输入一战晟铭密码。

采用设备配对：

```text
网页设置
→ 本地执行器
→ 绑定本机
→ 一次性验证码 / 二维码
→ 本地执行器确认
→ 绑定成功
```

绑定后保存设备凭证，后续自动连接。

网页可以显示：

```text
办公室电脑 ● 在线
家里电脑 ○ 离线
笔记本 ● 在线
```

并支持：

- 设为主设备
- 解除绑定

### 10.2 主设备优先 + 自动备用

多台设备同时在线时采用：

**主设备优先，主设备不可用时自动切换备用设备。**

必须有任务租约/执行权机制，确保同一份正文不会被两台设备同时重复同步或重复上传 121。

### 10.3 云端继续下的备用设备

云端继续模式中：

- 备用设备可以从云端临时正文恢复内容。
- 如果备用设备没有对应的一战晟铭用户的 121 会话，任务停在“需要登录 121”。
- 用户在该备用电脑的小说获取网页中完成一次 121 登录后，继续自动上传。

### 10.4 本地优先下的紧急转移

本地优先模式中，如果正文只在主设备，而主设备离线，备用设备不能自动获得正文。

用户可以显式点击“转移到备用设备”。

流程：

```text
主设备上传所需内部正文到临时中继
→ 备用设备下载
→ 校验哈希/长度
→ 确认接收成功
→ 云端中继立即删除
```

中继最长保留 24 小时。

- 成功接收后立即删除，不等 24 小时。
- 24 小时仍未接收则自动删除。
- 原主设备中的本地正文不受影响。
- 这是本地优先模式的人工例外，不是常规自动云存储。

## 11. 云端临时归档/正文管理

沿用现有“服务器归档”概念，但语义改为“用户自己的云端临时正文区”。

要求：

- 每个用户有固定的服务端根命名空间。
- 用户只能修改自己命名空间内的逻辑文件夹/分类，不允许输入任意系统路径逃出根目录。
- 可以看到哪些书/版本仍有云端正文。
- 可以查看到期时间。
- 可以单本删除、批量删除、全部清理。
- 可以主动下载到电脑。
- 删除云端正文不得删除用户电脑上的真实 TXT 或本地内部正文。

这个管理界面管理的是“正文对象”，不要求服务器真的为每个版本创建可见 `.txt` 文件。

## 12. 数据边界与安全

### 12.1 正文和历史分离

历史 API 默认不得返回完整正文，只返回元数据和正文可用状态。

读取完整正文必须使用专门的正文读取接口，并经过用户、书籍、版本权限校验。

### 12.2 设备隔离

所有本地任务必须至少按以下维度隔离：

```text
V78 用户
+ 设备 ID
+ 书籍 ID
+ 版本 ID
```

121 会话额外绑定 121 目标账号标识。

### 12.3 凭证处理

- 121 密码不写入历史记录。
- 121 密码不得写日志。
- 云端不长期保存 121 密码。
- 本地保存的是登录后的会话状态，而不是为了长期使用而明文保存密码。
- 本地设备凭证应由操作系统安全存储能力保护；至少不得明文写进普通配置文件。

### 12.4 删除语义

必须区分：

- 删除正文
- 删除历史
- 删除云端临时正文
- 删除本地内部正文
- 用户自己删除导出 TXT

这些动作不能互相隐式连锁。

尤其：

- **“清云端正文”绝不能删除用户电脑文件。**
- **“清除历史记录”只删除历史元数据，不直接删除正文。**

## 13. 建议的数据模型边界

实现时不要再用一个巨型 JSON 同时承载历史和正文。

建议至少拆成：

### 13.1 Task / History Metadata

轻量、长期保存。

包含任务状态、书籍信息、版本状态、121 状态、时间、错误摘要、正文可用标记等。

### 13.2 Body Object

可清理、可压缩。

建议键：

```text
userId
bookId
versionId          # original / ai1 / ai3 / ai5 ...
revision
contentHash
charCount
createdAt
lastNeededAt
releasableAt
expiresAt
storageLocation    # cloud / local / relay
state
```

正文内容与元数据分开。

### 13.3 Export Override

仅记录用户导出文件的定位信息和指纹，不把整个用户文件再次上传到云端作为历史。

例如：

```text
deviceId
bookId
versionId
exportPath
lastSeenMtime
lastSeenHash
state
```

### 13.4 Device Binding

记录设备、主设备优先级、最近在线时间、能力、租约状态。

### 13.5 121 Session Descriptor

云端只记录非敏感状态：

```text
deviceId
v78UserId
targetUsername
status
lastVerifiedAt
```

真实 browser storage state 保存在本地执行器。

## 14. 任务租约与防重复

多设备场景必须设计“同一动作只能有一个执行者”。

对以下动作加租约：

- 正文同步
- 正文恢复
- 设备转移
- 121 上传

租约至少包含：

```text
task/action id
assigned device id
lease token
lease expiry
attempt id
```

如果设备掉线，租约过期后备用设备才能接管。

121 上传应使用幂等/重复检测策略，避免主设备刚上传成功但回执丢失后，备用设备再次重复提交。

## 15. 错误与状态设计

用户可见状态应直接说明下一步，而不是暴露内部技术名。

建议状态：

```text
正在生产
等待本地执行器
正在同步到本机
等待 121 上传
121 需要登录
121 需要人工验证
上传失败，可重试
正文已清理
本地导出文件已不存在
备用设备接管中
转移已过期
因空间保护提前清理
```

“正文已清理”不是任务失败；历史仍然有效。

## 16. 迁移与上线策略

这次涉及云端存储、本地执行器、121 浏览器、多设备和设置，不能一次性切断旧路径。

建议分阶段：

### 阶段 1：正文/历史分层

- 建立独立 Body Store。
- 历史列表只依赖元数据。
- 保持现有服务器 121 Browser Worker 暂时可用。

### 阶段 2：本地执行器正文能力

- 设备配对。
- 本地内部正文存储。
- 云端到本地同步。
- 下载/导出 TXT。
- 导出文件优先规则。

### 阶段 3：121 本地化

- 网页登录入口不变。
- 登录命令发送给本地执行器。
- 本地 headless Chromium 登录和保存会话。
- 本地执行器读取正文并上传。
- 人工验证时可见浏览器兜底。

### 阶段 4：多设备与紧急转移

- 主设备优先 + 自动备用。
- 租约。
- 本地优先的 24 小时人工中继。

### 阶段 5：清理与容量保护

- 设置 → 小说获取 → 数据与清理。
- 1～30 天正文清理。
- 默认 7 天。
- 手动清历史（只清历史元数据）。
- 服务器容量保护。
- 清理审计状态。

### 阶段 6：移除服务器 121 Browser Worker

只有在本地 121 路径稳定、回退验证完成以后，才从生产部署中移除服务器 Browser Worker。

这样可进一步缩小服务器部署镜像和资源占用，但不能在本地路径未验证前提前删除旧能力。

## 17. 测试要求

### 17.1 正文与历史

- 删除正文后历史仍存在。
- 清除历史后，不直接删除正文。
- 历史列表不返回完整正文。
- `originalRaw` 不再与规范正文长期重复保存。
- 1 / 7 / 30 天清理策略正确。
- 清理计时从 `releasableAt` 开始，而不是正文生成时开始。
- 等待上传的正文不会被普通定时清理。
- 容量保护只清理安全对象。

### 17.2 TXT / 121 兼容

- 内部 AI3 无实体 TXT 仍可上传。
- 导出 `AI3.txt` 后手动修改，上传读取修改后的内容。
- 真正上传文件名仍为 `bookId.txt`。
- 上传字段仍为 `files[]`、`text/plain`、UTF-8。
- 用户删除导出文件后能够安全回退内部正文。

### 17.3 121 登录

- 正常登录不弹窗口。
- 会话保存在本地。
- 重启执行器后可复用会话。
- 会话失效后网页提示重新登录。
- 验证码场景可切换可见浏览器。
- 同一设备两个 V78 用户不会串 121 会话。

### 17.4 离线与多设备

- 云端继续：电脑关机后原文 + AI1/AI3/AI5 继续生产。
- 电脑关机期间不进行 121 上传。
- 电脑恢复后自动同步并继续上传。
- 主设备离线后备用设备不会与主设备重复执行同一上传。
- 备用设备缺少 121 会话时停在“需要登录 121”。
- 24 小时人工中继到期自动删除。

### 17.5 删除安全

- 清云端正文不删本地内部正文。
- 清云端正文不删导出 TXT。
- 清本地内部正文不删用户导出 TXT。
- 清除历史记录只删除历史元数据，不直接触发正文删除。

## 18. 非目标

本次不要求：

- 把 121 登录会话跨电脑复制。
- 让电脑关机时仍然上传 121。
- 默认给每个版本生成真实 TXT。
- 把用户手动下载的 TXT 纳入自动删除。
- 让普通用户关闭服务器全局容量保护。
- 在第一阶段立即删除现有服务器 Browser Worker。

## 19. 最终确认的关键规则

1. 默认没有真实 TXT；用户点击下载/导出才生成。
2. 用户已导出的 TXT 若存在，121 上传永远优先读取其当前内容。
3. 121 真正上传时仍临时命名为 `书籍ID.txt`。
4. 121 登录入口仍在小说获取网页；正常使用无头运行，不弹窗口。
5. 121 会话按“一战晟铭用户 + 设备”隔离，不跨电脑自动复制。
6. 云端继续时，电脑关机后原文和 AI1 / AI3 / AI5 继续完成，但 121 上传等待电脑上线。
7. 本地执行器开机自启、后台常驻、托盘显示状态。
8. 设备采用一次性验证码/二维码配对，不在执行器再次输入网站密码。
9. 多设备采用主设备优先 + 自动备用，并用租约防止重复上传。
10. 本地优先的人工设备转移使用最长 24 小时的临时中继，成功即删除。
11. 历史和正文分开；正文删掉后历史仍保留。
12. 导航“设置 → 小说获取 → 数据与清理”提供正文自动清理，默认 7 天，可设 1～30 天。
13. “清除历史记录”与“正文自动清理”相互独立；清历史不直接删正文。
14. 正文清理同时覆盖云端内部正文和本地执行器内部正文，但永不自动删除用户导出的 TXT。
15. 正文清理从正文不再被任务依赖的 `releasableAt` 开始计时。
16. 服务器达到安全容量阈值时可提前清理最旧的安全正文，不删历史。
17. 正文清理的主要目标是释放实际内部正文数据占用，而不是只删除可见 TXT 文件。
