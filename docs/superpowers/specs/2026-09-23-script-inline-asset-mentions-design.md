# 剧本编辑器内嵌素材 @ 提及设计

## 目标与成功标准

剧本页的总编辑和单分镜编辑需要提供类似即梦的素材提及体验：用户在任意文字位置输入 `@` 或点击 `@ 素材` 后，可从带主图缩略图、名称和类型的人物/场景候选中选择；选择后，编辑器正文在该位置显示“缩略图 + 名称”的内嵌素材块，而不是只显示纯文字或编辑器底部标签。

成功标准：

1. 总编辑和分镜编辑的候选菜单都紧贴当前正文 `@` 光标位置弹出，按输入过滤人物、场景；候选显示主图、名称和类型。
2. 选中已有主图的候选后，正文显示图片缩略图和 `@名称`；无主图时显示同尺寸的无图占位和名称，且不阻塞文字编辑。
3. 用户通过在正文任意位置输入 `@` 触发候选，并可通过键盘上下、回车、Esc 或鼠标点击完成选择；可插入多个素材。
4. 保存、复制、分镜拆分、草稿恢复和视频生成的规范文本仍是 `@名称`。现有 H3 引用图收集继续从人物/场景的 `mainImageUrl` 读取，并保留九张上限及用户禁用引用图的逻辑。
5. 无论 `@名称` 来自手动输入、粘贴、AI 生成、历史草稿或左侧资产后续更新，只要当前左侧人物/场景存在同名实体且该实体有主图，正文都自动显示该实体的缩略图素材块；用户不需要重新选择一次。
6. 不引入新的富文本依赖；不能使长剧本输入或页面 CPU 使用出现持续性明显增长。

## 已核对的参考实现与边界

小钟工作室 V3 提供了可视化的 `@` 候选：候选行使用素材主图、名称、类型，点击后插入结构化 `@` 文本；它自身仍是 `textarea`，因此不能在正文中显示图片。它适合作为候选卡和素材主图的交互参照，不能直接作为正文内嵌图片的实现。

当前 V88 `ScriptPage` 的总编辑与分镜编辑也使用 `Input.TextArea`，并通过 `scriptShotMentions.js` 维护文本光标和 `@名称` 替换。原生 textarea 不能在文本流内渲染图片，因此继续在其上增加标签或浮层无法达到目标。

`scriptVideoReferences.js` 已以剧本文字中的 `@名称` 匹配当前人物/场景，并从 `getEntityMedia(entity).mainImageUrl` 生成视频参考图。本设计不改变该协议。

## 方案比较

### 方案 A：自研轻量内嵌提及编辑器（采用）

新建一个受控的 React 编辑器组件，编辑模式使用 `contentEditable` 容器呈现正文。普通文本保持为文本节点，已匹配的 `@名称` 渲染为不可在内部修改的内嵌素材块；块中包含主图或占位、名称和类型语义。组件在输入、粘贴、选择候选和删除时把 DOM 规范化并序列化回唯一的纯文本值，并暴露当前光标的可视坐标以锚定候选菜单。

优点是无新依赖、可保持现有存储与视频协议、只渲染视口内已有文字和小缩略图。代价是需专门处理光标映射、删除一个素材块、粘贴纯文本与 IME 输入。

### 方案 B：引入 TipTap/Slate 等通用富文本框架

可获得成熟的选区和节点模型，但要引入大型依赖、将现有纯文本编辑/草稿/分镜接口迁移至富文本 JSON，再兼容复制和视频解析。对于只需要 `@` 令牌的剧本页过重，并增加包体和性能风险，不采用。

### 方案 C：继续保留 textarea，使用视觉叠层伪装图片

渲染层可看似显示缩略图，但鼠标选区、换行、高度、缩放和输入法光标都会与真实文本错位，无法可靠地支持“任意位置编辑”。不采用。

## 组件与数据流

### ScriptMentionEditor

新增可复用的 `ScriptMentionEditor`，用于总编辑和单分镜编辑。组件输入为：规范文本、人物/场景候选、当前是否可编辑、占位文字，以及 `onChange` / `onMentionQueryChange` / `onSelectCandidate` 回调。

组件职责：

1. 将规范文本按 `@名称` 分段。名称与当前人物/场景唯一匹配时渲染为内嵌素材块：无论该文本是直接输入、粘贴、AI 生成或从草稿恢复，均立即生效；其他 `@` 字样仍以普通文本显示，避免未匹配词被错误改写。
2. 内嵌块展示 `getEntityMedia(item).mainImageUrl` 的 22–24px 主图；无图时展示类型占位。块带可访问名称，例如“人物：妻子”。
3. 每次用户编辑后，把 DOM 还原为纯文本 `@名称` 并报告给上层。组件不保存独立富文本数据，也不向接口传 HTML。
4. 将 DOM 选区换算为规范文本位置，复用已有 `findActiveShotMention`、过滤与局部替换策略；候选提交后恢复光标到素材块之后。
5. 在素材块相邻位置按 Backspace/Delete 删除整个块，等价于删除规范文本中的完整 `@名称`；箭头键可跳过块。粘贴仅接收纯文本，自动移除 HTML 样式。
6. 组合输入期间不重建 DOM，直到 compositionend 后再规范化，防止中文输入法中断。

### MentionCandidateMenu

现有总编辑和分镜编辑分别维护的候选状态收敛为同一呈现组件，但保留各自的上层保存动作。输入 `@` 时，菜单以当前光标的 DOM Range 矩形为锚点，显示在该行下方；靠近编辑器下边缘时翻转到光标上方。它不能放在编辑器底部，也不随滚动脱离当前 `@`。

菜单结构与用户提供的参考一致：顶部文案“可能@的内容”；第一项为“＋ 创建主体”，用于打开既有的人物/场景创建入口；随后按匹配结果展示人物和场景卡，每张卡有主图/无图占位、名称、类型，右侧保留更多操作入口。候选为空时仍显示创建主体与无匹配说明。键盘上下键移动卡片焦点、回车选择、Esc 关闭，鼠标点击选择。

编辑器底部不保留 `@`、素材标签或其他与提及有关的工具按钮；素材入口仅为正文中输入的 `@`。原有的底部 `@ 素材` 和“当前全文已引用素材”文字标签均移除，避免与正文内嵌块重复。

### 规范文本与参考图

`output`、`editingShot.text`、本地草稿和复制内容均保持纯文本。用户在正文看到的图片只是当前左侧资产的实时视觉投影：页面加载、AI 生成、粘贴文本、创建同名资产、上传主图、替换主图任一发生后，所有已存在的 `@名称` 都在下一次渲染时自动匹配并显示新主图。实体删除、改名或尚未有图时，`@名称` 保留为普通文字或无图占位，绝不静默删除。

视频生成保持既有路径：分镜文本中的 `@名称` 经 `collectShotReferenceImages` 取实体主图。总编辑仍先按既有逻辑拆分/落入分镜，再生成视频。因此本升级不会额外上传图、不会改变 API 负载，也不会绕过用户在分镜参考图面板的禁用选择。

## 交互与错误处理

1. 候选为空时仍提供“＋ 创建主体”，并显示“没有匹配项，请先创建或提取人物/场景”；用户可继续把 `@` 当普通字符编辑。
2. 无主图候选可选，但正文显示无图占位；现有生成前检查继续提示“未选择主图”，不自动生成或上传图片。
3. 候选筛选不做网络请求，只使用已加载的 `extractInfo`，避免输入期间增加 CPU 或网络压力。
4. 图片使用懒加载、固定小尺寸和 `object-fit: cover`；加载失败回退类型占位，不影响编辑与保存。
5. 读取模式使用同一分段渲染器显示素材块，但不暴露可编辑 DOM；如该模式与当前分镜卡片视图冲突，分镜卡片以其现有独立视图为准。

## 测试与验收

新增纯函数和组件契约测试，至少覆盖：

1. `@` 查询、候选筛选和插入后的纯文本序列化；总编辑和分镜编辑共用同一规则。
2. 人物/场景候选菜单贴近正文 `@` 光标、会在底部空间不足时自动翻转；菜单含“可能@的内容”、创建主体入口、主图、类型和无图占位。
3. `@名称` 在正文被渲染为素材块，未知名称不被错误转为块。
4. 输入、粘贴、AI 生成或历史草稿中的 `@名称`，会在左侧同名资产具备主图时自动转为素材块；实体新增主图或更换主图后会自动刷新。
5. 在素材块前后插入文字、Backspace/Delete 删除块、粘贴纯文本、中文组合输入后的规范文本和光标位置。
6. 既有 `scriptVideoReferences` 回归：素材块视觉化后仍按 `@名称` 收集主图、去重并限制九张；无主图不进图片列表。
7. 执行相关 Node 测试与 `npm --prefix frontend run build`；上线前以本地交互验证总编辑和分镜编辑，但不自动触发真实视频生成。

## 非目标

- 不把完整图片或 HTML 存入剧本、草稿或后端。
- 不修改 Go API、模型配置、视频生成 API、TOS 上传通道或公网基础设施。
- 不替用户创建素材、上传图片或发起真实视频任务。
