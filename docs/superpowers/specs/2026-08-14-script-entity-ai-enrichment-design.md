# 剧本人物与场景智能补全设计

## 目标

在剧本生成页 `/script` 的现有人物与场景编辑弹窗中增加“根据小说智能补全”。用户手动填写名称、身份或用途后，可请求 AI 以当前上传小说原文为主要依据、以已有实体摘要为辅助上下文，生成可编辑的实体字段草稿。

## 范围

- 仅修改剧本生成页、`scriptEntities` 数据转换、前端生成 API 与 `/api/chat` 的现有 AI 请求链路。
- 新增单个实体智能补全请求与弹窗内草稿预览/应用交互。
- 保持现有人物、场景、主角白名单、草稿 localStorage、全文重新提取和剧本生成链路。

不新增服务端实体库、项目级人物资产、小说面板功能、跨项目共享实体或新的持久化 API。

## 手动内容保护

用户在实体编辑器中已填写的任何非空字段为人工锁定事实：

- AI 不得修改或覆盖锁定字段。
- AI 仅自动填入当前为空的字段。
- AI 对锁定字段存在不同判断时，写入独立的 `AI 建议`，不改变实体字段。
- 无法从小说原文确定的字段必须写入 `不确定项`，明确是推测而非原文事实。
- 智能补全结果仅存在于编辑弹窗本地状态；用户点击既有“保存”后才写入剧本草稿。

## 人物补全

人物至少需要名称；身份、外形和性格可以为空。请求内容包含小说原文、当前人物字段、现有人物与场景摘要、已选提取预设 ID。

AI 严格返回 JSON：

```json
{
  "fields": {
    "外形": "仅供填补空字段",
    "性格": "仅供填补空字段",
    "与主要人物关系": "仅供填补空字段",
    "可能别称": "仅供填补空字段"
  },
  "evidence": ["原文依据"],
  "suggestions": ["与人工锁定字段冲突时的建议"],
  "uncertainties": ["无法确认的推测"]
}
```

若用户填写“林薇 / 小三”，名称和身份绝不变化；AI 可补全外形、性格、关系和别称。AI 若认为她可能是秘书，只能写入 `suggestions`。

## 场景补全

场景至少需要名称；用途、时段、氛围、描述可以为空。请求内容同样以小说原文为主、已有实体摘要为辅助。

AI 返回：

```json
{
  "fields": {
    "时段": "仅供填补空字段",
    "氛围": "仅供填补空字段",
    "描述": "空间、光线、陈设、关键道具和视觉提示词"
  },
  "evidence": ["原文依据"],
  "suggestions": [],
  "uncertainties": []
}
```

若用户填写“酒店套房 / 男女主冲突地点”，用途不会变化；AI 仅补全空的时段、氛围和描述。

## 前端交互

实体编辑弹窗新增“根据小说智能补全”按钮和三个只读区：

- 原文依据；
- AI 建议；
- 不确定项。

按钮仅在小说原文非空、实体名称非空且未请求时可点击。请求期间按钮禁用并显示加载状态；失败时显示错误并保留所有手动编辑内容。

收到响应后，前端对 `fields` 按字段应用：仅当当前字段为空时写入编辑器草稿。`evidence`、`suggestions`、`uncertainties` 只显示在编辑器中，不强制保存到实体数据。用户可以继续编辑，再点击现有保存按钮；保存后的实体继续通过 `normalizeExtractInfo` 和账号草稿保存机制参与剧本生成。

## API 与安全

新增 `/api/chat` 的 `promptType: "entity_enrich"`，请求字段：

```json
{
  "promptType": "entity_enrich",
  "entityType": "character | scene",
  "novelText": "小说原文",
  "entity": { "当前实体字段": "值" },
  "existingEntitySummary": { "characters": [], "scenes": [] },
  "extractionPreset": "当前已发布提取预设ID"
}
```

服务端：

1. 使用现有 `apiAuth`、限流、当前账号模型配置和上游调用机制。
2. 验证 `entityType` 仅为 `character` 或 `scene`，验证小说原文和名称非空，并对文本、字段数、摘要数量做上限限制。
3. 使用当前已发布且协议为 `extract` 的预设正文作为 AI 协议基础；不接受前端传入的预设正文。
4. 在系统提示词明确原文优先、不能篡改人工非空字段、未知信息必须放在 `uncertainties`，并要求严格 JSON。
5. 解析 AI 内容后只返回字段建议、依据、建议和不确定项；不写入用户草稿或实体数据。
6. 复用现有上游错误处理；不记录 API Key、小说原文、完整实体正文或上游原始错误。

## 与剧本生成的关系

保存后的实体仍通过：

```text
EntityEditor → extractInfo → localStorage draft → toGenerationEntities() → /api/chat promptType: script
```

因此主角星标、普通人物、场景信息和现有的服务端 `sanitizeProtagonists()` 保护保持不变。实体变化后仍按现有规则清空旧输出并回退为已提取状态。

## 测试

1. 前端字段合并测试：AI 只能填空字段，不能覆盖“名称”“身份”“用途”等人工非空字段。
2. 前端请求测试：人物/场景请求携带原文、实体、摘要和已选预设 ID；无原文或无名称时不可请求。
3. 后端消息测试：`entity_enrich` 使用已发布提取预设，且提示词包含原文优先、字段保护和不确定项约束。
4. 后端输入测试：非法实体类型、缺少原文/名称、过长文本、无效预设均返回安全 400；不调用上游。
5. 后端解析测试：严格 JSON 返回映射为 `fields/evidence/suggestions/uncertainties`；不写入持久化存储。
6. 回归测试：现有实体管理、主角白名单、草稿持久化、提取预设和剧本生成请求测试全部通过。
