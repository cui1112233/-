# 巨量素材执行器本机更新设计

## 目标

Windows 与 macOS 的巨量素材执行器各自在本机提示可用更新；用户在该执行器窗口点击更新后，仅更新当前电脑的应用。更新不得要求重新下载压缩包、重新配对或重新下载已安装的 OCR 运行时。

## 已确认规则

- 网页设置页只展示设备在线状态、系统与版本，不提供“更新所有设备”或远程替设备更新的操作。
- 每个执行器独立检查更新；离线、闲置或不再使用的电脑不会被远程强制更新。
- 首次配对后，设备凭据保存在用户配置目录；常规应用升级必须保留该凭据。
- 完全删除用户配置或服务端撤销凭据时，才要求重新配对。
- 正在运行 OCR 或上传结果时不应用更新；用户可稍后更新。

## 设备身份边界

同一电脑的稳定身份由应用保存的设备 ID 与本机凭据证明，不采集或展示硬盘序列号、MAC 地址等硬件指纹。服务端以“账号 + 操作系统 + 设备名”合并现有历史记录；应用升级只是更新该设备的版本与心跳。

设备页默认只显示当前可用设备。历史 Token 记录只用于审计，不计入“已绑定设备”。任务领取后，界面必须显示领取设备的名称、系统、版本和领取时间；任务仅在尚未领取时显示“等待在线执行器”。

## 本机更新流程

```text
执行器启动或恢复空闲
  -> 拉取受信更新清单
  -> 当前版本低于可用版本时，显示本机更新提示
  -> 用户点击“立即更新”
  -> 下载当前系统/架构的安装包，校验 SHA-256 与发布签名
  -> 检查没有运行中的 OCR 任务
  -> 启动短生命周期更新助手，退出执行器
  -> 更新助手替换当前应用并重新启动
  -> 新版本读取原设备凭据并自动恢复在线
```

更新清单至少包含版本、目标系统/架构、下载 URL、SHA-256、签名和最小兼容版本。执行器内置更新公钥；下载包或清单的校验失败时保留旧版本、显示错误并不执行替换。

## 平台实现

### Windows

沿用现有更新助手思路：主程序空闲时下载并校验，交由独立 `apply-update` 进程替换可执行文件后重启。用户级 DPAPI 凭据目录不在替换范围内。

### macOS

macOS 使用随应用发布的小型更新助手。主应用退出后，助手原子替换 `GiantMaterialExecutor.app` 并重新打开它；用户配置目录和 macOS Keychain 不在应用包内，因此不会丢失设备凭据。若安装位置无写权限、应用未通过发布签名校验或替换失败，显示明确错误并保留旧版本。

## 用户界面

执行器本机窗口显示：

```text
已连接：ming 的 Mac · macOS · 0.5.3
发现新版本 0.5.4
[立即更新] [稍后提醒]
```

下载时显示进度；完成后显示“正在重启并恢复连接”。运行任务时按钮替换为“任务完成后可更新”。网页设置页仅可显示“此设备有可用更新”，不能触发更新。

## 非目标

- 不对其他账号或其他已绑定设备推送、安装或强制更新。
- 不以硬件指纹替代用户授权。
- 不把设备 Token、配对码或更新私钥下发到浏览器。
- 不在本设计中改变巨量 OCR 的内容获取、书城备用获取或生产范围语义；这些另行设计。

## 验收

1. 已绑定设备升级后仍使用原 `ExecutorID`，无需配对。
2. 一台电脑点击更新，另一台绑定电脑版本与运行状态不变。
3. 执行中任务不会被中断；更新按钮在任务结束后恢复可用。
4. 清单签名、安装包哈希或应用替换失败时，旧版本仍可启动且凭据不丢失。
5. macOS 与 Windows 均能更新、重启并自动恢复在线。
6. 网页只能显示更新可用状态，不能代表用户操作另一台设备进行安装。
