# 批量定时全自动：正文直取优先设计

## 目标

对已选择“全自动生成并提交”的巨量批次，每本书在不启动本地 OCR 执行器时仍能尽可能完成：服务端直取正文、资产提取、导演分镜、视频生成、合成、121 上传及回执确认。不能直取正文或任一阶段最终失败的书必须立即标记失败并释放并发名额，不能无限等待。

## 已确认边界

- 直取到正文才允许进入 AI 和发布阶段；不能把没有正文的书伪造成已完成。
- 现有 `full_submit` 模式已经包含合成后的 121 上传和回执读取；只有真实确认才显示上传成功。
- OCR 是直取失败后的可选补救，不是定时自动化的前置条件；本次不要求启动执行器。
- 单书失败不停止同一批的其他书，且不覆盖已完成阶段和既有上传回执。

## 方案比较

1. 推荐：自动化运行时对缺正文的书复用现有服务端“获取正文”能力；成功后回到正常流水线，失败后该书终止并继续下一本。
   - 无需浏览器常开或本地执行器，复用已有书城平台、清洗和原子保存规则。
2. 仅把 OCR 等待改成失败。
   - 能释放队列，但仍无法让可直取的书进入生产，不能达成目标。
3. 强制重派 OCR。
   - 依赖被用户明确关闭的本地执行器，且会再次引入无限等待，不采用。

## 数据流与状态

`缺正文` → `服务端直取` → 成功：保存正文与来源元数据、下一轮进入资产阶段 → `生成/合成` → `full_submit`：调用 121 → 逐文件回执确认：`uploaded`。

直取失败：若已有活跃且未过期的 OCR 任务，可保留其已有回填；否则该书记为 `failed/source`，记录直取失败原因，释放名额。任何阶段的短暂服务错误仍使用现有有限重试；超过次数则失败让位。

## 实现范围

- 将 V12 已验证的书城正文获取/清洗/原子回填逻辑抽为服务端共享模块。
- 给 V11 自动化适配器增加“直取并回填正文”能力。
- 调度器在 OCR 协调之前先执行直取；预检也使用相同规则，避免队尾书被 OCR 占位卡住。
- 补回归测试：直取成功时无需执行器并进入上传链；直取失败时只失败该书并继续后续书；保留 121 回执成功的既有语义。

## 验收

- 关闭执行器的批次中，可直取书不出现“等待 OCR”，而是自动进入生产。
- 无法直取的单书显示具体失败原因，后续书继续运行。
- `full_submit` 批次仅在 121 成功回执后计入上传成功；没有回执不能伪报成功。
- 针对测试、构建、已登录公网的批次状态检查均通过后，才部署；不修改作品数据卷或重建数据库。
