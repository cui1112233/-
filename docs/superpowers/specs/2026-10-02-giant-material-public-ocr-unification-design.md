# 巨量素材：公网 OCR 与本机测试统一设计

- 日期：2026-10-02
- 状态：已与用户确认，待实现计划与开发
- 范围：`巨量获取`的正文读取、滚屏 OCR 派发、状态展示、正文回填和后续自动化衔接

## 1. 要解决的问题

`/giant-material-test` 已证明某些巨量素材可以在开发机直接完成“青语解析 -> 视频读取 -> 本机滚屏 OCR -> 正文展示”。但它是 Vite 本机回环测试路由，直接调用本机的 OCR 提取器；公网批量工厂改走“公网任务 -> 已配对执行器 -> 回传正文”的另一条链路。

因此“本地测试成功、公网批量正文为空”并不矛盾，但不能作为正式产品行为保留。正式用户路径必须取得与本机测试一致的正文结果，且不能要求用户手动点“改用滚屏 OCR”。

## 2. 已确认的用户结果

用户在新建批量中选择“巨量获取”、输入一个或多个巨量素材 ID、选择内容范围并点“立即执行”后：

1. 系统解析素材，获得书名、Book ID、书城、视频地址和时长。
2. 先按书城读取原文。
3. 书城没有正文或读取失败时，自动将同一本书转为滚屏 OCR；用户不需要额外点击。
4. OCR 成功后保存完整正文，再按照当前批量的行数与字数范围供制作使用。
5. 正文就绪的书自动进入既有 AI 判断、资产、分镜、视频、合成与上传流程；未就绪或失败的书不阻塞其他书。
6. 用户始终能看到当前阶段、使用中的电脑和真实失败原因；不会把“尚未派出 OCR”“执行器失败”和“AI 模型令牌失败”显示成同一种错误。

## 3. 方案选择

采用“统一 OCR 内核 + 公网执行器调度”。

### 3.1 采用的方案

将本机测试页所使用的滚屏提取能力抽为可复用的 OCR 内核。测试页仍可直接调用它用于开发验证；macOS / Windows 巨量执行器也调用同一内核完成正式任务。公网服务不下载和长期保存视频，不承担本机 OCR，而是负责：鉴权、创建任务、选择在线执行器、记录进度、接收正文及触发后续自动化。

这样保留本机执行器的速度和成本优势，同时消除两套 OCR 行为漂移。

### 3.2 放弃的方案

1. **只修状态条或派发接口。** 改动小，但本地页和正式执行器仍是两种 OCR 逻辑，下一次仍可能“本地成功、公网失败”。
2. **让公网服务器自己跑 OCR。** 省去执行器，但视频流量、存储、CPU 和并发都压在公网，速度与成本不符合本项目的本机执行器方向。

## 4. 正式数据流

```text
巨量素材 ID
  -> 青语解析（书名 / Book ID / 书城 / 视频 / 时长）
  -> 按书城直接读取正文
       -> 成功：保存完整原文 -> 按内容范围供制作 -> 自动化
       -> 失败：创建 OCR 任务 -> 选择在线执行器
                    -> 执行器用统一 OCR 内核读取和整理
                    -> 回传完整原文 -> 保存 -> 按内容范围供制作 -> 自动化
```

### 4.1 正文保存与内容范围

- 保存 `originalRaw`（完整、清理后的识别正文），不保存 MP4、帧图、青语令牌或浏览器 Cookie。
- 制作输入从 `originalRaw` 按当前书的内容行数和 `maxTxt` 截取；浏览器不自行决定权威截取结果。
- 详情页和列表显示“原文已就绪：总 X 字；本次制作：前 N 行 / Y 字”，避免将完整识别量与制作输入量混淆。
- 识别结果清理必须去掉 HTML 实体、单独标点行、重复滚屏片段和运行状态文案；不得改写原剧情文本。

### 4.2 自动化衔接

- 仅当正文成功保存后，巨量书从 `waiting/source` 进入 AI 判断。
- 新建“立即执行”批量沿用既有自动化计划；每本正文回填后独立推进，不等待整批 OCR 完成。
- 历史批量不会在无用户动作时补发付费生产；可重试“正文读取”或“OCR”后，按其已保存的自动化计划继续。
- `Invalid token` 等文本模型错误归入 AI 判断阶段，不能覆盖或伪装为正文读取 / OCR 错误。

## 5. 任务状态和用户界面

### 5.1 持久化状态

每本巨量书的来源元数据必须持久化以下阶段和诊断信息，刷新后不丢失：

| 内部阶段 | 用户展示 | 必填诊断 |
|---|---|---|
| `direct_reading` | 正在按书城读取原文 | 书城、Book ID |
| `direct_read_failed` | 书城未取到正文，正在转 OCR | 上游稳定错误码 / 可读原因 |
| `ocr_dispatching` | 正在交给本机执行器 | 候选执行器平台 |
| `ocr_queued` | 已排队，等待某台执行器 | job ID、目标/可领取平台 |
| `ocr_claimed` | 已由 <设备名> 接手 | executor ID、设备名、平台 |
| `ocr_processing` | 滚屏 OCR 识别中 | 处理秒数、总时长、进度 |
| `ocr_cleaning` | 正在整理正文 | 已识别字数 |
| `ocr_returned` | 正文已就绪 | 原文总字数、完成时间 |
| `ocr_dispatch_failed` | 无法派发 OCR | 稳定错误码和可读原因 |
| `ocr_failed` | OCR 失败 | job ID、设备名、失败阶段与原因 |

未获得 `job ID` 的状态绝不能显示为“OCR 失败”；它必须显示为“无法派发 OCR”或“等待执行器”，让用户知道问题发生在什么边界。

### 5.2 列表与详情展示

- 小说列表“内容”列只显示一行紧凑状态，不再塞狭窄的状态卡：`正在读取正文`、`已由 ming 的 Mac 识别 62%`、`正文已就绪`、`读取失败`。
- 点“查看”打开详情，展示横向状态卡、完整错误、正文预览、Book ID、书城、来源和任务 ID。
- 原文已就绪显示“原文”标签；失败时只显示与当前失败阶段匹配的动作：
  - 直接读取失败：`重试获取原文`；
  - OCR 派发或 OCR 执行失败：`重试 OCR`；
  - 不提供会重复创建书或重复启动已完成制作的操作。
- 状态卡复用已确认的共享阶段语义，完整页与紧凑列表不重复定义颜色和文字。

## 6. 执行器选择、绑定和更新

本设计不重新定义设备配对协议，沿用并实现《巨量素材执行器：Mac/Win 双平台切换 + 同机身份合并》：

- 一台电脑由稳定设备身份识别；同账号、同系统、同设备名的重新配对更新凭证和版本，不新增设备。
- 账号可设 Windows 或 macOS 优先；偏好设备在线且可用时优先领取，离线或近期开工失败时另一平台可接手。
- 一台执行器串行处理 OCR；其他任务保留 `ocr_queued`，不因为等待而失败。
- 升级由执行器自身检查版本并在空闲时完成；升级不要求重新生成配对码，也不影响既有身份。

## 7. 安全和错误边界

- 青语授权令牌仅存在于受控服务端或本机密钥配置；前端、日志、数据库、任务错误和 Git 均不出现令牌值。
- `/giant-material-test` 继续限于本机回环开发用途，不成为公网绕过执行器的入口。
- 创建任务必须校验已解析的 Book ID、书城、视频 URL 与时长；无有效视频时不创建伪 OCR 任务。
- 执行器断线时已领取任务依据租约回到可领取队列；进行中的任务不被另一台电脑强行抢走。
- 相同巨量素材再次提交复用已有书或失败任务，只重跑失败阶段，不新增重复小说。

## 8. 验收与发布

### 8.1 自动化验收

1. 直接书城正文成功：不创建 OCR 任务，正文保存并启动该书自动化。
2. 直接读取失败：创建 OCR 任务并持久化 `ocr_queued`，页面刷新后仍可见 job ID 和阶段。
3. 无在线执行器：任务停在等待 / 排队，不显示为 OCR 识别失败。
4. 执行器领取并回传统一 OCR 结果：完整正文保存、内容范围正确、自动化仅对该书启动。
5. 任务派发失败、执行器失败、回传失败和模型令牌失败分别映射为不同阶段和可读提示。
6. 多 ID 串行 OCR：一本失败不阻塞其他书；成功书继续自动化。
7. 同机重新配对、平台优先与离线回退回归通过。
8. 前端构建、Go / Node 相关单测及 OCR 内核契约测试通过；测试中不出现授权令牌。

### 8.2 公网验收

1. 发布后以精确 Git SHA 验证公网 build-info。
2. 先用一条授权巨量素材验证“公网派发 -> 指定在线 Mac 或 Windows -> 正文回传 -> 小说详情可见”。
3. 在确认正文正确后，再由用户明确触发会调用付费模型的完整自动制作验收。
4. 正式发布走 `v88` 的 Stage -> Cutover 增量流程；不把 ECS 运行文件当源码，也不以全量 Docker 重建作为默认方式。

## 9. 范围外

- 不把 OCR 改为公网服务器常驻计算。
- 不保存视频、帧图或 OCR 模型输出文件。
- 不绕过青语授权或要求普通用户通过 F12 提供令牌。
- 不把模型令牌错误伪修成 OCR 错误；模型配置另行修复。
