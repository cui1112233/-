# 正式部署与数据保护设计

## 目标

将 `http://10.0.101.164:3000` 固定为长期正式服务。部署、重启和应用升级不得清空或覆盖用户账号、会话、小说、批次、项目、模型配置、任务记录或视频对象。

## 根因

当前正式地址误用 `docker-compose.test.yml` 与 `deploy/.env.test-docker`。该配置允许测试卷初始化、密钥重新生成和 `down -v` 清卷。平台和后端曾以不同的 MySQL 密码、桥接密钥运行，造成后端重启、内部请求 401，以及前端把水货接口失败显示为登录过期。

## 环境边界

| 环境 | 用途 | Compose | 环境文件 | 数据卷 |
| --- | --- | --- | --- | --- |
| production | `10.0.101.164:3000` 长期服务 | `deploy/docker-compose.production.yml` | `deploy/.env.production` | `qiantie-production-*` |
| test | 本地开发与回归测试 | `deploy/docker-compose.test.yml` | `deploy/.env.test-docker` | `qiantie-test-*` |

正式环境与测试环境不得共享端口、环境文件、容器名、网络或 Docker 卷。正式脚本拒绝读取 `.env.test-docker`；测试脚本拒绝占用正式端口。

## 配置与会话

`.env.production` 仅在首次初始化时生成，之后作为主机受限文件保存，不写入 Git。下列值必须在平台和后端完全一致且不得在普通发布中重新生成：

- `QIANTIE_BRIDGE_SECRET`
- `QIANTIE_TOKEN_SECRET`
- `MYSQL_PASSWORD`
- `MYSQL_ROOT_PASSWORD`
- `QIANTIE_CREDENTIAL_ENCRYPTION_KEY`

平台数据卷持久保存 `sessions.json`、账号配置、批次适配数据与任务元数据。平台与后端容器可替换；MySQL、Redis、平台数据和对象存储卷不可因应用发布而删除。

## 数据保护流程

### 发布前

1. 读取正式 Compose 解析后的环境，确认平台与后端桥接密钥一致。
2. 检查正式 MySQL、平台数据、对象存储和 Redis 卷存在，拒绝初始化空卷覆盖已有正式卷。
3. 使用只读账户统计账号、模型、小说获取任务、水货项目、批次、批次书籍与对象数量，写入发布基线 JSON。
4. 生成带时间戳的 MySQL 一致性逻辑备份，并校验备份文件非空且可列出表结构。
5. 记录当前平台与后端镜像摘要作为回滚目标。

### 发布

1. 构建新平台与后端镜像，不修改数据卷。
2. 先替换后端容器，等待数据库、Redis、对象存储和桥接健康检查通过。
3. 再替换平台容器，保留平台数据卷和环境文件。
4. 不执行 `docker compose down -v`、`docker volume rm`、MySQL 初始化或环境文件重新生成。

### 发布后

1. 检查 `/healthz`、平台首页、登录会话和水货项目接口。
2. 用实际登录会话验证水货转发接口不返回 401。
3. 对比正式数据基线；账号、模型、任务、项目、批次和对象计数不得下降。
4. 验证批量工厂可加载真实批次或显示真实空状态，不允许样例数据。

## 失败与回滚

若构建、容器健康、内部桥接或数据基线任一检查失败，停止发布。仅将平台/后端镜像回滚为发布前摘要；不回滚、不删除、不重建正式数据卷。MySQL 备份用于人工确认的数据恢复，不作为自动覆盖手段。

## 验收标准

- 连续重启平台与后端后，已勾选“记住登录”的正式会话仍然有效。
- 平台与后端使用相同桥接密钥，水货接口不出现内部鉴权 401。
- 后端能够使用正式 MySQL 账号持续健康运行。
- 发布前后数据基线一致或仅允许业务新增。
- 测试脚本无法操作正式 Docker 卷或正式端口。

## 非目标

- 不在本次部署改造中接入 121 上传发布。
- 不修改批量工厂既有四栏视觉框架。
- 不擅自设置本地豆包执行器的视频时长能力；该能力需由管理员按实际执行器限制配置。
