# 管理端系统预设词闭环设计

## 目标

将当前硬编码或文件型系统预设词迁入 qiantie 已有的受保护预设词库。管理员可在管理端创建、编辑、发布和回滚预设词；后端在后续生成请求中自动使用已发布版本。普通用户只能使用或选择预设词元信息，不能读取、提交或导出预设词正文。

本期接入范围：

1. 快速剧本生成：人物场景提取、连续开头、爆款开头、通用规则、剧情模式、画布模式、剧本模式。
2. 小说面板：内容分析、人物卡、分镜生成。
3. 水货生产保留 Go 服务自己的预设词实现和存储边界，本期不由 Express 管理端写入。

## 方案比较

### 方案 A：仅允许修改 prompts 文件

优点是实现快。缺点是没有权限、版本、审计或回滚，且修改要依赖文件系统权限，不能满足管理端运营。

### 方案 B：管理端编辑，保存即覆盖线上正文

优点是操作直接。缺点是错误保存会立即影响生产请求，无法形成审核和可靠回滚。

### 方案 C：受保护版本库，草稿和发布分离

管理员编辑正文时创建新草稿版本，发布后切换当前生产版本，历史版本自动归档并可回滚。该方案复用现有 `preset-store`、能力授权和审计机制，推荐采用。

## 管理端

在管理端导航增加“系统预设词”。页面按模块展示预设词列表，显示名称、用途、类别、版本、状态、兼容关系和最近发布时间。

拥有 `preset:draft` 的管理员可新建或编辑自己获授权模块的预设词。编辑弹窗包含预设词 ID、名称、模块、基础/补充类别、适用说明、兼容基础预设词、系统预设词正文和协议锁说明。

保存只创建草稿。拥有 `preset:publish` 的管理员可发布草稿，或将某一归档版本回滚为已发布版本。正文只由管理员专用 API 返回；无权限和普通用户的任何 API 响应都不得包含 `body` 或 `protocolLock`。

## 后端模型与数据流

1. 启动时将既有 10 类默认预设词以固定 ID 写入预设库，仅当该 ID 尚无版本时初始化，绝不覆盖已经发布或草稿中的管理员版本。
2. 每类预设词都有固定用途 ID。快速剧本生成按请求类型、开头模式和输出格式解析所需预设词；小说面板按分析、人物或分镜操作解析所需预设词。
3. 生成请求只从服务器预设库读取当前发布版本正文，并组合为 system message。请求体中的用户小说、角色、场景和项目补充要求仍进入 user message。
4. 若当前用途尚无已发布预设词，则使用受控的内置默认正文，保证首次部署和旧系统继续可用。初始化成功后，后续发布版本优先。
5. 管理员发布或回滚会同步写入版本与审计记录。下一次生成请求重新解析已发布版本，因此无需重启服务，也不会影响已经发出的模型请求。

## 约束与安全

- `body` 和 `protocolLock` 是服务器机密字段，不下发给普通用户浏览器。
- 预设词 ID、模块和预设用途是服务端白名单；前端不能指定任意正文或跨模块预设。
- 小说面板的 JSON 结构、质量闸门和人物身份协议作为 `protocolLock` 受保护。草稿正文不能移除或反转该协议锁。
- 编辑、发布和回滚全部经过既有能力检查；权限不足返回 403。
- 现有 `prompts/*.md` 只作为一次性默认种子来源，不再作为运行时唯一真源。
- 现有用户调用接口保持不变，避免影响剧本生成、小说面板、登录、历史和配音。

## 验收与测试

1. 未授权账号无法读取、创建、发布或回滚任一预设词正文。
2. 有模块草稿权限的账号只能创建对应模块草稿；无发布权限不得发布。
3. 管理员编辑并发布后，下一次剧本或小说面板请求使用新正文；草稿不生效。
4. 回滚后，下一次请求使用目标历史版本。
5. 普通用户的预设目录和解析接口不包含 `body`、`protocolLock`。
6. 旧提示词文件在无发布版本时仍能提供默认行为。
7. 覆盖后端单元和路由测试、前端构建，以及管理员页面的浏览器验证。

## 非目标

- 本期不把水货生产的 Go 预设词正文改由 Express 管理。
- 本期不允许普通用户编辑系统预设词正文。
- 本期不修改模型 API、Bearer 注入、小说面板 iframe 隔离或质量闸门协议。
