# 巨量素材单次导入队列去重设计

## 目标

同一次“巨量素材获取”弹窗提交中，重复巨量素材或解析为同一平台书籍的素材必须只登记一次；重复项不再次 OCR、创建执行器任务或新建小说记录。

## 已确认口径

- 输入巨量素材 ID 先按规范化后的 ID 去重；标题不参与去重。
- 每一个保留 ID 解析成功后，按返回的 `platformBookId` 再去重；同一书 ID 仅保留队列中的第一条素材。
- 同名但 `platformBookId` 不同的素材可以同时导入。
- 历史批次不参与本次判定：历史中出现过同一巨量 ID 或同一书 ID 均允许再次导入。
- 范围只限本次弹窗的单个提交队列；不改动历史数据，也不新增跨账号或跨批次唯一约束。

## 根因

当前队列仅在输入阶段按巨量素材 ID 组织条目；不同巨量 ID 即使解析为同一 `platformBookId`，仍会依次登记、OCR 和创建执行器任务。当前批次的 `source_book_id` 防重发生在 OCR 之后，既浪费读取，也不能给队列展示明确的“既有素材”跳过结果。

## 方案

保留现有输入 ID 规范化和队列解析；在解析完成、用户已选择平台书籍后，记录本次执行上下文中的 `platformBookId`。若该书 ID 已由本次队列前一项占用，当前项立即标记为“既有素材，已跳过”，并且不创建占位书、不派发 OCR、不创建 intake。

判定只使用该次 `executeQueue` 调用中的内存集合，不读写历史批次，也不改变 MySQL 的跨批次唯一性。当前批次已有相同书 ID 时仍沿用现有 append 冲突保护；本修复只把可预知的同一次导入重复前移到 OCR 之前。

## 测试与验收

1. 队列测试证明：重复输入巨量 ID 仅保留一项。
2. 前端流程测试证明：两个不同巨量 ID 解析为同一 `platformBookId` 时，后者不调用 OCR 或 intake 创建，并显示为 skipped。
3. 测试证明：同名但不同 `platformBookId` 的两项均可继续读取；历史批次数据不会影响本次判定。
4. 回归运行相关 Node 单测和前端构建。
5. 生产发布后，在已登录 UI 一次提交两个解析为同一书 ID 的测试素材，核验只有一个 OCR job 和一个新书记录，另一条显示跳过；不触发付费生成。

## 非目标

- 不删除、合并或阻止既有历史记录。
- 不按标题合并、删除或覆盖小说。
- 不改变 OCR、自动生产或视频供应商行为。
