# 巨量自动化预设：创建即冻结并可见

## 背景与问题

巨量素材的“立即执行”曾先创建批量，再由浏览器发起第二个请求保存自动化预设。若第二个请求失败、页面刷新或使用旧版页面，批量已经存在，却没有统一配置、没有单书可继承的有效配置，也没有可靠的自动化计划。

这会造成三个用户可见问题：统一配置为空、单书配置看似未配置、正文完成后无法按原计划自动生产。

## 目标

选择预设并点击“立即执行”后，批量只能在以下内容都已经保存时才进入正文读取、OCR 或自动生产：

1. 统一配置的完整预设快照；
2. 预设名称、ID、版本与冻结时间；
3. 巨量自动化计划（执行模式、并行数、定时信息）；
4. 单书可解析的有效继承配置。

已创建批量必须继续使用自己的冻结配置；后来编辑或删除原预设不得改变它，也不得使恢复任务失败。

## 方案选择

采用服务端原子创建，而不采用前端重试或失败后删除批量。

- 浏览器只提交选中的预设 ID、执行方式与巨量书资料。
- Node 服务端读取该账户已保存的预设，冻结配置与版本，并把创建请求转交给 Go V11 API。
- Go 在同一数据库事务内创建批量、写入 batch settings patch 与预设快照元数据；事务失败则整次创建失败。
- Go 返回已含 `settingsState` 的批量后，浏览器才派发直接书城读取或 OCR。浏览器不得再以独立请求补写统一配置。

自动化恢复从批量冻结的 settings/plan 读取，不再依赖当前预设仓库仍存在同一个 `presetId`。

## 界面语义

- 统一配置显示批量被冻结的真实值，并显示“来源预设：名称 · v版本 · 已冻结”。
- 单书配置显示最终生效值；没有单书覆盖时标记“继承统一配置”，不显示成“未配置”。
- 历史批量若不存在冻结快照，显示明确说明：该批次创建时没有保存预设，不能安全还原；允许用户手动应用预设，但不自动猜测或启动生产。

## 失败边界

- 预设不存在、已无有效配置或保存事务失败：创建请求失败；不创建 OCR 任务、不开始自动生产。
- 预设后来被修改或删除：已创建批量仍从冻结快照执行。
- 旧批量：保持原数据与执行状态；仅增加可理解的提示与手动修复入口。

## 验证

先写并观察以下失败测试，再实现：

1. 巨量立即执行的创建 API 返回批量时，统一 settings 和冻结预设元数据已存在。
2. 保存预设失败时，批量、OCR 任务与自动化任务均不会产生。
3. 删除原预设后，恢复器仍按批量冻结配置启动。
4. 单书有效配置合并统一设置，且 UI 显示“继承统一配置”。

实现后运行 Node 定向测试、Go V11/HTTP API 定向测试、前端构建；再用一个不调用模型的公网创建/读取验收确认配置刷新后仍存在。日常发布只按变更范围增量更新 Node/Go，绝不重建 MySQL、Redis、数据卷或完整 Docker 镜像。
