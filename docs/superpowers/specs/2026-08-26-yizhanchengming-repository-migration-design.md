# 一战晟铭仓库迁移与恢复保护设计

## 目标

将当前已发布的源码历史安全迁移到 `https://github.com/cui1112233/yizhanchengming`，建立清晰的稳定发布与开发主线，同时不覆盖目标仓库既有 `main`，不把运行数据或凭据提交到 Git。

## 已确认边界

- 当前运行基线：Docker 已发布的 `integration/remote-workbench-20260819` 对应提交；迁移前必须重新核对实际容器构建的提交与工作树状态。
- 目标仓库已有 `main` 和 `migration/phase-1-clean-foundation`，两者均不得被强推、重写或删除。
- Git 只保存源码、测试、文档和非敏感配置模板。
- 账号、会话、提示词运行数据、上传文件、对象存储、MySQL、Redis、Docker 卷和私密环境变量不进入 Git。

## 仓库结构

| 分支 / 标签 | 用途 | 保护策略 |
| --- | --- | --- |
| `main` | 新仓库稳定发布主线 | 保留既有历史，只通过审查后的合并更新 |
| `develop` | 后续日常开发主线 | 从确认的迁移基线建立，功能分支合并后删除 |
| `migration/legacy-published-20260826` | 当前旧系统已发布源码基线 | 创建后不改写 |
| `archive/legacy-branches-20260826` | 仅在确有恢复价值时保存的旧分支快照 | 只读，不作为开发线 |
| `legacy-published-20260826` 标签 | 已验证发布点 | 注释标签，不移动 |

不迁移旧仓库全部特性分支。先按提交差异、生产功能覆盖和测试状态筛选；无法证明仍有价值的分支保留在旧仓库，不复制到新仓库。

## 数据保护

迁移前创建两类独立、可校验的备份：

1. Git 恢复点：记录旧仓库当前 HEAD、已发布提交、远程分支引用和目标仓库当前 HEAD；创建迁移标签和仅源码归档分支。
2. 运行数据恢复点：导出 MySQL、保存 Docker volume/对象文件清单、备份部署私密环境文件到不受 Git 管理的加密位置，并校验归档可读性。

备份清单只记录文件名、时间、校验和与恢复步骤，绝不记录密码、令牌、Cookie 或 API Key。

## 迁移流程

1. 只读盘点旧/新仓库分支、提交关系、工作树、`.gitignore` 与 Docker 数据挂载。
2. 执行并验证运行数据备份，生成恢复清单。
3. 添加目标仓库为新 remote，先推送不可变迁移基线分支与注释标签，不触碰目标 `main`。
4. 在独立工作树中基于迁移基线建立 `develop`，运行测试、前端构建和 Docker 部署验证。
5. 经确认后，再以可审查合并把稳定内容接入新仓库 `main`；禁止强推。
6. 旧仓库设置为只读历史来源；新仓库确认稳定后，按归档清单删除新仓库中已合并的临时功能分支。旧仓库不删除分支。

## 失败与回滚

- 推送失败：不修改现有 remote，不重写任何分支，使用记录的 SHA 重试。
- 新仓库部署失败：继续使用旧仓库对应 Docker 镜像；新仓库迁移分支保留供修复，不合并 `main`。
- 运行数据恢复失败：停止清理步骤，使用校验后的备份重新恢复到隔离环境；不得对生产数据执行 `clean`。

## 验收

- 新仓库含可追溯的已发布源码标签和迁移基线，目标原有 `main` 历史未改变。
- `develop` 能完成受影响测试、前端构建和 Docker 健康检查。
- 运行数据不出现在 `git ls-files`、提交差异或 GitHub 历史。
- 恢复清单可定位 Git、MySQL 与对象数据的对应备份，且校验通过。
